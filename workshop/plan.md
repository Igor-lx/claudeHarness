# План приёмки обвязки — метод

Метод одного прогона приёмки: довести обвязку до рабочего состояния на нашем
стеке и показать это числами. Принят разработчиком `2026-11-02`, поправлен по
итогам первого прогона и `2026-11-06`. Файл лежит в `workshop/`: он про
мастерскую и с обвязкой не едет.

**Метод и прогон лежат порознь.** Здесь — шаги, справки, решения; из этого
файла ничего не удаляют. Состояние прогона — оставшиеся шаги и данные этого
прогона — в `.claude/state/todo.md`, раздел «Прогон плана приёмки».

- **Завести прогон** — по слову разработчика: в todo раздел «Прогон плана
  приёмки» со списком всех номеров шагов отсюда, по порядку, и пустыми
  данными прогона; затем шаг `1.1`.
- **Шаг сделан** — его номер удаляется из списка в todo той же правкой.
- **Поправка метода по ходу работы** — правится этот файл, тем же коммитом,
  что и работа, которая её вызвала. Так поправка действует и на текущий
  прогон, и на следующий; второй копии метода нет нигде.
- **Данные прогона** — новый составной проект, новые проекты корпуса,
  выбранные посадки, кандидаты проходов — пишутся в todo, а не сюда: у
  каждого прогона они свои (раздел «Предмет исследования — новый каждый
  прогон»).
- **Прогон закончен** — раздел прогона из todo удаляется целиком.

## Как вести работу

План написан для сессии, у которой нет истории той, что его вела: всё
нужное лежит здесь, в todo, в `CLAUDE.md` мастерской и в файлах по названным
адресам.

**Перед первым шагом сессии — сброс к `origin/main`.** Каждый шаг пушится
сразу, поэтому всё неотправленное в контейнере — незаконченный шаг либо
остаток прежней работы, и оно сбрасывается, а не разбирается (решено
разработчиком `2026-11-02`): `git fetch origin --prune`,
`git checkout -B main origin/main`, `git reset --hard origin/main`,
`git clean -fdx`, прочие локальные ветки удалить. Перед `git clean -fdx`
посмотреть `git clean -ndx`: снимки `workshop/*.bundle` под версионированием
и не теряются, а испытательная посадка лежит вне репозитория. Незаконченный
шаг начинается заново.

**Затем прочитать `CLAUDE.md` в корне мастерской.** Его правила план
исполняет и не повторяет: ветка одна — `main`; работа планируется до начала,
и дорогое действие стоит один раз на группу; работа идёт по одному шагу —
следующий после исхода предыдущего, включая CI; цель — рабочее состояние по
трём условиям; область гарантий — наш стек, чужое отсекается классом;
превышение бюджета доктрины разбирается до сокращения.

**Что читать на входе.** Todo — целиком: это состояние прогона. Из плана —
этот раздел «Как вести работу» и пункт своего шага; справки — по ссылке,
когда шаг их называет. План целиком не читают: `88 000` знаков на каждый
перезапуск сессии.

### Шаг — единица работы

Пункт разбит на шаги с номерами вида `2.3`. Порядок исполнения:

1. Взять первый номер из списка оставшихся в todo. Шаги и пункты идут по
   порядку: каждый следующий опирается на сделанное предыдущими.
2. Сделать шаг целиком: работа, находки шага, их починка классом, тесты
   затронутого по имени.
3. Удалить номер шага из списка в todo той же правкой. Результат шага —
   числа, находки, что починено и как — пишется в сообщение коммита; в todo
   — только данные, которые читают следующие шаги.
4. Коммит и `git push origin main` — после **каждого** шага, без отдельного
   спроса: это прямая команда разработчика на весь план (`2026-11-02`). Новых
   веток не заводить, даже если среда сессии назначила свою (`CLAUDE.md`).
5. Шаг не помещается в остаток сессии — разбить его в todo на части,
   сделанную часть удалить, оставшуюся записать номером с буквой, коммит и
   push. Следующая сессия начинает с первого оставшегося номера, ничего не
   восстанавливая по памяти.

Сообщения коммитов — английские, Conventional Commits, как в истории
мастерской.

**Ответ разработчику кончается отдельной строкой состояния:** что идёт
сейчас, кто делает следующий шаг и нужна ли команда разработчика — например
«Сейчас: жду CI прогона N и в такое-то время сам продолжаю; команда не
нужна». Решено разработчиком `2026-11-07`: без неё, ждёт ли сессия, стоит
или ждёт ответа, приходилось искать в середине текста.

### Перезапуск сессии — в точках плана

Решено разработчиком `2026-11-09`. Цена обращения — объём контекста сессии.
Замерено: стартовый контекст — `107 540` токенов (доктрина и правила), а
одна сессия на весь прогон дошла до `727 000` на обращение. Свежая сессия с
todo и своим пунктом плана — по оценке около `150 000`: каждое обращение в
`4`–`5` раз дешевле. Поэтому прогон идёт цепочкой сессий: в точке
перезапуска сессия останавливается, а следующую запускает разработчик.

**Точки перезапуска** — после каждой:

| Пункт | Точка |
| --- | --- |
| 1–6 | граница пунктов — всегда |
| 2 | семейство холодной оси; шаги 2.3, 2.4; каждая сессия 2.5 |
| 3 | 3.1 с 3.2 вместе; каждый свод 3.3; 3.4; 3.5 |
| 4 | 4.1 с 4.2 вместе; 4.3; 4.4; 4.5; 4.6; 4.7 |
| 5 | каждые два работника; горячий раунд |
| 6 | каждый подшаг |

**Остановка безопасна, только когда всё знание сессии в репозитории:**
итог шага в данных прогона todo; шаг снят из «Оставшихся шагов»; коммит
запушен; его CI дал исход либо в todo записано «ждёт CI на `<коммит>`» —
тогда следующая сессия начинает с исхода CI; находка без починки записана
словами — что, где, как чинить, что пробовали; незаконченный код не
коммитится, а ложится патчем в `workshop/` с пометкой в todo. Не
останавливаются: между находкой и коммитом её починки; пока идёт работник
`claude -p`, свод, полный набор или `falsify` — сперва их итог и запись;
между посадкой, сводом и судом `bar-probe` — песочница живёт в контейнере,
и остановка выбросила бы свод; пока работник ждёт ответа — его журнал для
`--resume` тоже в контейнере, диалог с работником доводят до конца одной
сессией.

**Как останавливается.** В точке перезапуска, выполнив условия выше, сессия
кончает ответ строкой состояния, а за ней — двумя строками, последней
именно этой:

```
продолжай план из .claude/state/todo.md с первого оставшегося шага, метод — workshop/plan.md
ПЕРЕЗАПУСТИТЬ
```

Первая — фраза, которой разработчик запускает следующую сессию.

**Площадки при перезапуске.** Предмет между шагами один и тот же:

| Площадка | Переживает перезапуск | Новая сессия |
| --- | --- | --- |
| составной проект пунктов 4 и 5 | снимком `workshop/composite-*.bundle` — состояние после последней сессии, с историей | поднимает порядком `.claude/README.md`, раздел «Мастерская и проекты»: клон, `npm ci`, `core.hooksPath`; снимок после каждой сессии, меняющей проект, обязателен до остановки; полка клона — редакции снимка, правка полки после снимка требует её обновить (шаг 5.1) |
| испытательная посадка | нет; однозначна от полки на коммите | `seat <папка>`, справка, шаг 2.1 |
| стенд проб | нет; однозначен от `bar-stand.json` и книги | `bar-probe --stand-build` |
| песочницы `bar-probe`, площадки работников | не нужны: заводятся заново под каждый свод и работника | как и без перезапуска |

Собирать лениво: только ту площадку, которая нужна шагу, при первой нужде,
а не все разом на входе. Сборка стоит одно-два обращения сессии.

**Цена — токены, а не время** (решено разработчиком `2026-11-09`). Время
машины и ожидания ценой не считается; выбор между вариантами — по токенам
сессии и сохранности знания, на которой стоят надёжность и верность
результата. Отсюда: перезапуск — в каждой точке, пересборка площадок —
сколько нужно; проверку отдают машине — тест, `verify`, полный набор —
вместо разбора чтением в контексте; ожидание CI — одним пробуждением к
ожидаемому концу, без опросов; знание не жертвуют ради токенов — то, что
сессия узнала, ложится в todo до остановки.

Держится: вниманием — сессия сама проверяет, стоит ли в точке.

### Проверки и публикация

- **По ходу шага и перед его коммитом** — тесты затронутого по имени:
  `npx vitest run --config .claude/tools/vitest.config.mjs -t "<имя>"` в
  испытательной посадке, и сверка базы там же. Испытательную посадку перед
  этим обновляют командой шага `2.1`: иначе тест проходит, не найдя своего.
- **Полный набор — один раз на пачку, последним её шагом.** Пачки плана:
  пункты `2` и `3` вместе; пункт `4`; пункт `5`; пункт `6` — если в нём
  что-то правилось после последнего полного набора.
- **CI — одна проверка Windows на пачку правок инструмента** (решено
  разработчиком `2026-11-06`). Push, тронувший `.claude/tools/**` или
  `.claude/seat/**`, запускает `harness-windows` — полный набор на Windows,
  около `60` минут — и при своих путях `harness-bootstrap`. Пачка — группа
  независимых правок по правилу `CLAUDE.md` о дорогих действиях:
  промежуточные коммиты пачки несут `[skip ci]` в заголовке, последний — без
  него, и его сообщение говорит, что этот push — один запуск Windows на
  такие-то коммиты. Следующая пачка, стоящая на инструменте, начинается после
  исхода CI. Цена: промежуточный коммит на Windows не проверен; ту же цену
  `CLAUDE.md` уже принял для полного набора.
- **Отступление от `safety.md` принято разработчиком `2026-11-02`.** Там
  публикация наружу — только после полного набора с кодом ноль. Здесь
  промежуточный push идёт после тестов по имени, чтобы работа не терялась
  между сессиями и аккаунтами; страховка — CI на пачку.
- **Красный CI или красный полный набор — следующий шаг, впереди всех
  остальных.** Статус CI смотрят инструментом GitHub (`actions_list`, ветка
  `main`).
- **Сообщение коммита последнего шага пачки называет, сколько раз
  запускалось каждое дорогое действие и почему не меньше** — графа отчёта из
  `CLAUDE.md`.

### Находки

Чинятся классом, порядком скилла `probe`, раздел «Найденное лечится как
класс, а не как пример»: класс одной фразой; места рода — командой поиска;
сведение в один механизм; тест на механизм; фальсификация четырьмя
действиями. Находка, которая воспроизводится только в чужом окружении,
чинится только как отсечение: не упасть, не встать посреди работы, назвать в
отчёте (`CLAUDE.md`, «Область гарантий»). Шаг, который сессия-работник
выполнила одним вниманием, — кандидат в машинный держатель: ворота, хук,
сверку.

**Замечание сессии об инструменте — сначала проверка, потом находка.**
Сессии свода и работники называют «поломки» инструмента; в первом прогоне
подтвердилась примерно половина. Каждое замечание воспроизводят до того, как
назвать находкой; неподтверждённое называют в коммите с причиной.

### Сессии-работники и наблюдатель

Кто такие работник и наблюдатель, как зовут работника, сводка журнала и
перечень шагов с признаками — скилл `probe`, раздел «Работник и
наблюдатель». Наблюдатель здесь — сессия, ведущая план. Образец вызова для
площадок плана — справка «Команды и площадки».

**Наблюдатель даёт работнику то, без чего тот по доктрине встаёт:** ответ на
вопрос фазы 2 «что это за проект» — строкой задания либо вторым сообщением, —
и команду коммита, если задание её требует. Без этого меряется не процесс, а
законная остановка.

### Экономия — необходимо и достаточно

Решено разработчиком `2026-11-02`: площадка несёт ровно предметы своих
проверок, по одному экземпляру на форму, и код, который не читает ни одна
проверка, не пишется; наблюдатель читает сводку журнала, а не журнал; проба
читает только то, о чём её вопрос; дорогое действие — раз на группу
(`CLAUDE.md`). Строгость при этом не снижается: число проб и посадок
выведено из того, что нужно утверждать (справка «Числа и что они позволяют
утверждать»), а не из бюджета.

### Предмет исследования — новый каждый прогон

Решено разработчиком `2026-11-06`. **Инструменты и окружение
переиспользуются**: испытательная посадка, скрипты, команды, конфиги
мутаций, скиллы. **Предмет исследования пишется заново**: составной проект,
новые проекты корпуса, посадки `bar-probe`, пробы и проходы холодной оси,
задания работникам. Причина: по предметам прошлого прогона обвязку уже
чинили, и прогон на них подтверждает починку, а не ищет новое.

- Новый предмет несёт те же формы, что требует метод, на другом коде, с
  другими именами и с дефектами других критериев.
- Чем прошлый предмет был, видно по истории: в справках ниже названы
  коммиты образцов. Их читают, чтобы понять масштаб, и не копируют.
- Конкретика нового предмета — данные прогона в todo.

### Решения плана — без разработчика не пересматривать

- **Порядок:** 1 → 2 и 3 одной пачкой починок → 4 → 5 → 6. Суждение о коде
  (пункт 3) меряется раньше процесса (пункты 4–5): работники опираются на
  свод, и промах свода смешался бы с промахом процесса (`2026-11-02`).
- **Магазин (`seat --shop`) не используется.** Площадка процесса — составной
  проект после приведения: он меньше, и заодно проверяется, что приведённый
  проект живёт как написанный с нуля (`2026-11-02`).
- **Числа:** холодная ось — проходы по видам, хотя бы один на семейство, и
  выборка из `21` пробы, по `3` на семейство, с добором по находке
  (`2026-11-06`, вместо `49` проб до первого чистого); `bar-probe` — `30`
  новых посадок в `4` сводах по родам (`2026-11-06`); сессий-работников `12`:
  `2` в пункте `2`, `4` в пункте `4`, `6` в пункте `5`; горячий раунд —
  проход по держателям-машинам и работник на хуки (`2026-11-06`, вместо `7`
  проб); отдельный горячий прогон 7×7 не делается. Почему именно столько —
  справка «Числа и что они позволяют утверждать».
- **Наблюдатель — сессия, ведущая план, по перечню.** Машинная проверка
  журнала заводится только на шаг, который работник пропустил или выполнил
  одним вниманием (`2026-11-02`).
- **Версия выше связки обходится как версия ниже:** план стека, согласие
  (`--apply`), приведение к связке; отказ — решение в реестре. Это обещание
  знакомого сценария из `CLAUDE.md`; инструмент, делающий иначе, чинится.
- **Ручную посадку в IDE на Windows разработчик проводит сам, отдельно.** В
  план она не входит.

## 1. Подготовка: ожидания, перечень шагов, составной проект, сводка журнала

Что именно: всё, без чего следующие пункты судили бы на глаз. Дорогих
действий в пункте нет.

**1.1. CI зелёный на последнем коммите `main`** — на последнем коммите,
который запускал `harness-windows` и `harness-bootstrap`: коммиты с
`[skip ci]` и коммиты вне их путей не запускают ничего, и их дерево
проверяет следующий запуск. Красный — разобрать лог и починить первым.

**1.2. Опись корпуса против форм знакомого проекта.** Формы — уровни шести
факторов:

| Фактор | Уровни |
| --- | --- |
| окружение | полное · без части звеньев (Prettier, Stryker, линтер, раннер) |
| версии | ниже связки · как в связке · выше связки · диапазоном и точно |
| раскладка папок | наша (`src/app`, `src/components`, `src/shared`) · плоская `src` · корень исходников не `src` |
| место тестов | `tests/` своего слоя · рядом с файлом · `__tests__` · корневая `tests` |
| стили | наша схема (модуль стилей в папке компонента) · глобальный CSS · карта классов пропом · объект стилей в разметке · SCSS без модулей · CSS-in-JS · без интерфейса |
| конфиги | файлы семени · другие имена и форматы |

Опись — командой по `.claude/tools/foreign-corpus.json`: у каждого проекта
сценарий, файлы и зависимости манифеста. Каждый уровень, которого нет, и
каждое сочетание уровней, которого нет у знакомых проектов, — новый проект в
данные прогона, к шагу 2.3. Уровни, которые уже несут проекты прошлых
прогонов, получают проект в новом сочетании: предмет новый каждый прогон.

**1.3. Версия выше связки.** Установить по коду посадки (`graph.seat.mjs` —
`stackSurveyOf`, план стека; `lintBlockersOf`; `graph.profile.mjs` —
сценарий), что она делает с пакетом выше связки. Выбрать пакеты связки, у
которых опубликована версия выше: `npm view <пакет> version`; связка — поле
`verifiedVersions` семени настройки. Брать пакеты, которых выше связки ещё
не несёт ни один проект корпуса. Выбор — в данные прогона: один пакет для
составного проекта, один для проекта корпуса шага 2.3. Нет такого ни у

## 3. Суждение о коде: 30 новых посадок `bar-probe` в четырёх сводах

Что именно: условие «смысловая верность», часть «находит ли свод дефект в
коде — по строке и по уровням узла, слоя, приложения». Порядок — скилл
`bar-probe`.

**3.1. Выбор критериев и новые посадки.** `node .claude/tools/graph.mjs
bar-hold` в испытательной посадке. Взять критерии, где «чисто» стоит на
чтении либо вопросе модели, а не на машине: машинные держит тест обвязки.
Приоритет — уровни узла, слоя и приложения; затем критерии, чей держатель
правился после прошлого прогона. `30` критериев раскладываются по четырём
сводам: в существующем коде; редкие роды — удаление, сосед, перенос; новым
файлом; добор в существующем коде. На каждый критерий пишется новая посадка
в книгу `.claude/tools/bar-probes.json` — нарушение, которого не было в
прошлых прогонах (номера прошлых — в их коммитах), — и проходит ворота
стенда `bar-probe --stand-check`. Номера и критерии — в данные прогона.

**3.2. Стенд.** `node .claude/tools/graph.mjs bar-probe --stand-build
<пустая папка вне репозитория>` — код `0`.

**3.3. Четыре свода, по одному на подшаг.** Каждый: посадить пачку
`--batch=<номера>` (пачка из разных родов идёт без ключа рода); свод делает
сессия по заданию из скилла `bar-probe`, раздел «Задание сессии свода»,
дословно; суд `bar-probe <номер>`; строка цены
`bar-probe --cost --session=<uuid>` — в `.claude/rationale/loop.md`, раздел
«Соразмерность: что читать под задачу» (обязательна по скиллу); коммит и
push. **Промахи и замечания свода об инструменте проверяются, и
подтвердившиеся чинятся до посадки следующей пачки** — с тестами и после
исхода CI на починке (правило `CLAUDE.md` «Работа идёт по одному шагу…»,
решено разработчиком `2026-11-02`): иначе дефект инструмента повторится
промахом в следующих сводах.

- 3.3.1. В существующем коде.
- 3.3.2. Редкие роды: удаление, сосед, перенос.
- 3.3.3. Новым файлом.
- 3.3.4. Добор в существующем коде.

**3.4. Разбор того, что осталось от сводов.** Класс — какой формы нарушения
не увидел держатель критерия; места рода — критерии, чей держатель не видит
той же формы, перечнем `bar-hold`; починка в держателе, а не под посадку;
посадка в книгу на каждую форму рода, через ворота стенда.

**3.5. Перепроверка одной пачкой.** Промахнувшиеся посадки плюс посадки
критериев с тем же держателем. Промах снова — одиночная проба этого
критерия.

**3.6. Полный набор пачки пунктов 2–3.** Испытательную посадку обновить
командой шага 2.1, затем полный набор (справка «Команды и площадки»).
Красное — чинить, перезапуская только упавшее, затем коммит и push.

## 4. Знакомый проект: переход и приведение до «как с нуля»

Что именно: условие «посадка» и «смысловая верность» на знакомом проекте с
чужой раскладкой и чужими стилями — **обе стадии**. Переход по
`.claude/seat/transition.md` кончается тем, что обвязка знает проект, а
расхождения записаны долгом с планами; код проекта он не меняет. Приведение
— обычная работа по пунктам долга, по слову разработчика (`code.md` и
`styles.md`, разделы «Проект, устроенный иначе»): пункт приведён — строку
удаляют и обнуляют храповик; обе таблицы пусты — файл перехода удаляют.
Проверяется, что переход записал долг верно, а работа по нему довела проект
до состояния «как с нуля».

Сессия `1` изображает только переход: код проекта она не меняет, итог —
база и долг. Сессии `2`–`4` изображают следующую за ним команду
разработчика «почини»: структура папок вместе с местом тестов, стили,
остальной долг. Итог всех четырёх — проект, неотличимый от посаженного в
пустую папку и написанного с нуля; это мерит шаг 4.6. Разбивка на сессии
приблизительная: перенос трогает каждый файл кода, и по правилу «долг
перехода от починки не защищает» (`loop.md`) сессия `2` закрывает тем же
заходом и прочие пункты в этих файлах; сессия `4` сверяет оставшееся с кодом
и берёт то, что не закрыто.

Сессии идут цепочкой: каждая работает на результате предыдущей. Находку,
мешающую следующему звену, чинят до него — тесты по имени, коммит, push;
если починка меняет то, что сделала прошлая сессия, эту сессию повторяют.
Прочие находки ждут шага 4.7. После каждой сессии состояние площадки
сохраняется снимком в `workshop/` (справка «Команды и площадки»); снимки
нового прогона заменяют снимки прошлого под теми же именами.

**4.1. Площадка.** Собрать площадку из проекта `composite` порядком

- каждое отклонение стоит пунктом долга с числом, держателем и планом по

**4.4. Сессия 3 — стили.** Задание: «переведи стили на схему обвязки —

## 5. Процесс: шесть работников и горячий раунд

Что именно: условие «смысловая верность», часть «сессия проходит порядок
работы без пропуска шагов». Рефактор, правку стиля и багфикс уже прошли
сессии пункта `4` со второй по четвёртую; здесь — остальные роды задачи.

**5.1. Площадка.** Для каждого работника — свежий клон базовой точки
порядком восстановления из `.claude/README.md`, раздел «Мастерская и
проекты»: клон не несёт `core.hooksPath`, и без неё ворота перед коммитом не
стоят. Сессии независимы: ни одна не видит правок другой. Полка клона —
редакции снимка; если полка правилась после снимка (`git log` по `.claude/`
от коммита снимка), клон сперва получает текущую полку правилом повторного
вызова `seat` (`.claude/tools/graph.md`, режим `seat`): файлы полки
копируются поверх `.claude` клона, снятое на полке снимается, файлы проекта
внутри обвязки — поле `projectOwnedInsideHarness` карты посадки — остаются.
Сам режим клон не обновит: метки посадки у клона нет, — поэтому разовым
скриптом. Обновление коммитится в клоне, `verify` и `npm run check` в нём —
код `0`, и снимок базовой точки сохраняется заново: иначе работники мерят
прежнюю обвязку, а каждая следующая сессия обновляет полку ещё раз.

**5.2. Работник «новый узел» — первым.** Задание вида: «добавь компонент
<новый, связанный с предметом проекта, из данных прогона>; по завершении
закоммить». Заодно замер цены сессии (`bar-probe --cost`); число — в
сообщение коммита. Провалился машинный шаг — ворота, хук конца хода, печать
— остальные пять не запускаются до его починки.

**5.3. Остальные пять работников подряд, один шаг на всех.** Задания
пишутся по именам базовой точки — их называет её карта
(`.context/00-map.md`) — и лежат в данных прогона:

- удаление узла — «удали <компонент>, он больше не нужен; закоммить»;
- правка значения-настройки — «подними <настройку> с <было> до <стало>;
  закоммить»;
- правка теста — «тест <компонента> проверяет только отрисовку — добавь
  проверку <действия>; закоммить»;
- ревью без правки — «сделай ревью <компонента>, ничего не меняя»;
- правка одной документации — «допиши в документацию <компонента>, зачем
  у него <два варианта>; закоммить».

Наблюдатель читает пять сводок за один проход, после последней сессии.

**5.4. Горячий раунд — проход по держателям-машинам и работник на хуки.**
Порядок — скилл `probe`, правило «Точку, которую держит машина, пробой
руками не берут — её держателя проходят списком»: перечень держателей
командой, у каждого — фальсификация (рецепт `falsify` либо тест
инструмента), держатель без неё получает тест. В перечень входят и точки,
которые прошлый прогон брал пробами:

1. `blast` — радиус у узла с потребителями в разных слоях.
2. `cycles` и `dead` — посаженный цикл и экспорт без потребителя названы.
3. `repoint` — строки, вставленные над якорем, переставлены; `tiers`
   печатает цену ярусов.
4. База в прямую сторону: файл без записи в карте — сверка его называет.
5. База в обратную сторону: запись о файле, которого нет, — сверка её
   называет.
6. Страж: коммит кода с `--no-verify` и с `-c core.hooksPath=` остановлен.
7. Ворота конца хода: ход с неопечатанной правкой кода удержан;
   `stop --pause` с причиной печатается началом следующей сессии; правило,
   изменённое посреди сессии, страж называет.

Руками ставится только проба `7` — сессией-работником в посаженной
площадке: хуки исполняются только в живой сессии, а в мастерской их нет.
Правило меняют на диске посреди хода работника, а не по таймеру: короткая
сессия кончается раньше, и часть пробы проходит мимо. Если ход работника
этого не позволяет — ворота и паузу пробуют живой сессией, а смену правила
прямым вызовом `node .claude/tools/hook.mjs guard --hook`, и в коммите
сказано, какая часть чем проверена (так сделано `2026-11-04`).

Коммит — с пометкой `Probe-run: hot; …`.

**5.5. Разбор по классам → починки → полный набор пачки пункта 5 → повтор
только тех сценариев, где был пропуск → коммит и push.** Шаг, выполненный
работником одним вниманием, получает машинного держателя либо остаётся с
записанной причиной, почему машина его не видит.

Готово, когда: у каждого шага каждого рода исход «выполнено» и держатель

## Справка: составной проект — что строить

Площадка пункта 4 и база работников пункта 5: знакомый проект, который
переход обязан прочитать, записать долгом с планами, а сессии 2–4 — привести
до «как с нуля». Пишется заново каждый прогон: другое приложение, другие
имена, дефект другого критерия. Образцы прошлых прогонов — `a0cd12a`
(карточка магазина, `2026-11-02`) и `7f577ad` (привычки за неделю,
`2026-11-06`): смотреть масштаб, не копировать.

**Размер.** Проект несёт ровно предметы проверок, по одному экземпляру на
форму; код, который не читает ни одна проверка, не пишется. `12`–`17`
файлов, до `300` строк. Небольшое приложение на React с одним предметом,
которое описывается одной строкой задания. Код пишется чистым по типам и
линту: долг типов и линта держит корпус, и здесь он не нужен.

**Что проект обязан нести** — каждая строка одним экземпляром:

| Форма | Чем несётся | Ожидается после перехода |
| --- | --- | --- |
| стек ниже связки | манифест: React `18`, Vite `5`, Vitest `2`, TypeScript `5.6` | план стека поднимает по согласию |
| пакет выше связки | манифест: пакет из шага 1.3 | план стека опускает к связке |
| версии диапазоном | манифест: `^` у всех пакетов | пакеты осей закреплены посадкой; пакет вне осей — пункт «Версии зависимостей диапазоном» |
| без части звеньев | нет Prettier и Stryker | звенья ставит план стека |
| точка входа в корне src | `index.html`, main.tsx | пункт «Раскладка проекта своя» |
| корень композиции не в src/app | App.tsx с глобальным листом, где лежат классы одного из компонентов | раскладка; схема стилей |
| компонент с вариантом пропом и стилями глобальными классами | файл компонента в корне src; два варианта пропом (размер, тон) | раскладка; схема стилей (папка компонента) |
| тест рядом с файлом, проверяющий только отрисовку | тест того же компонента; нажатие не проверено | «Тесты вне папки `tests/`»; работник правки теста дописывает проверку действия |
| карта классов пропом | компонент получает карту из App; тип карты — запись по любой строке | схема стилей; «Ключи переданной карты классов названы типом компонента» |
| объявление над функцией узла | константа уровня модуля в файле компонента | «В файле узла только сам узел» |
| объект стилей в разметке | третий компонент со стилем объектом | схема стилей (папка компонента) |
| хук без тестов, читающий настройку | хук предмета приложения с пределом из файла настроек | файлы без тестов; «Код под мутациями не мерян» |
| значение-настройка | файл настроек с числом, которое работник правки настройки меняет | файлы без тестов либо документ настроек |
| сборная папка | utils, common, lib — общий код без области | раскладка; возможен факт `levels` «общий узел одной единицы» |
| тест в `__tests__` | тест функции сборной папки | «Тесты вне папки `tests/`» |
| дефект, находимый чтением по планке | функция сборной папки нарушает один критерий планки; каждый прогон — другой критерий (`2026-11-02` — `E2`, `2026-11-06` — `C4`) | пункт долга с критерием и файлом |
| слабый тест | тест той же функции, который дефекта не ловит (`J1`) | пункт долга либо пункт мутаций |
| конфиги своими именами | конфиги сборщика, компилятора, линта проекта | слиты с конфигами обвязки, а не переписаны |

**Что требуют задания пунктов 4–5** — проект обязан это иметь: компонент с

## Справка: числа и что они позволяют утверждать

Предметы проверки трёх родов, и считаются они по-разному.

**Детерминированное** — посадка командой, сверки, `falsify`, самопроверки:
тот же вход даёт тот же исход, повтор ничего не добавляет. Мерило — каждый
класс входа один раз: ветка посадки, достижимая входом человека, держится
тестом либо проектом корпуса (шаг 2.4).

**Стохастическое** — сессии модели. Правило трёх: ноль провалов в `n`
независимых попытках — доля провалов не выше `3/n` с уверенностью `95` %:
`15` попыток — `20` %, `30` — `10` %, `49` — `6` %, `60` — `5` %. Попытки
внутри одной сессии зависимы, поэтому их раскладывают по нескольким
сессиям.

**Поисковое** — холодная ось `probe`: найти неизвестное. Проход по виду
перечисляет его целиком и закрывает тестом — это детерминированное. Выборка
ищет виды, о которых не подумали: чистая выборка из `21` пробы — доля
неизвестного не выше `14` % на пробу. Повтор прогона — по слову
разработчика.

| Что | Сколько | Почему |
| --- | --- | --- |
| холодная ось | проходы, хотя бы один на семейство, и `21` проба, по `3` на семейство, с добором | проход закрывает вид целиком; `21` чистая — не выше `14` %; скилл `probe` |
| корпус | по проекту на ветку кода посадки | шаг 2.4 |
| `bar-probe` | `30` новых посадок, `4` свода | `10` % без поправки на зависимость внутри свода; цена свода почти не зависит от числа посадок |
| посадки сессией | `2` | знакомый проект сажает сессия пункта 4 |
| переход и приведение | `4` сессии цепочкой | одна сессия на стадию; пункты долга сверяет машина |
| работники процесса | `6` | роды задачи, не пройденные в пункте 4 |
| горячий раунд | проход по держателям-машинам и `1` работник на хуки | точку, которую держит машина, держит её фальсификация, а не проба |
| полный набор | `4` раза, пятый — если правил пункт 6 | раз на пачку |
| `falsify`, мутации инструмента, `handoff`, `bar-hold` | по `1` разу | |

Цена, замеры первого прогона: свод пробы планки — `$3.4`–`$4.8` за пачку;
сессии перехода и приведения — `9.79`, `14.38`, `17.98`, `3.13` доллара;
работники — от `1.09` (документация) до `6.20` (новый узел) доллара.

**Что будет можно утверждать по итогу:**

1. Посадка: каждая ветка посадки, достижимая входом человека, держится
   тестом либо проектом корпуса, и каждый проект корпуса садится кодом `0` —
   детерминированно.
2. Переход и приведение: знакомый проект с чужой раскладкой и тремя чужими
   формами стилей проходит переход и доходит до «как с нуля» по машинному
   критерию шага 4.6.
3. Суждение свода: `0` промахов на `30` новых посадках — доля промахов не
   выше `10` % (`95` %) без поправки на зависимость внутри свода.
4. Процесс: каждый шаг каждого рода задачи либо держит машина, либо он
   наблюдался без пропуска, с границей `3/n`.
5. Холодный контур: каждый перечисленный вид пройден целиком и держится
   тестом; выборка из `21` пробы нашла столько-то новых видов, а чистая —
   доля неизвестного не выше `14` % на пробу.

## Справка: ловушки сборки площадок

Каждая уже стоила упавшего прогона либо потерянного времени.

**Перед полным набором — дешёвые проверки, которые его роняли.** Полный
набор идёт около `25` минут, CI на Windows — около `65`, и красный в любом из
них стоит повтора обоих. Поэтому до полного набора, по тому, что тронуто:

1. обновить испытательную посадку командой шага 2.1;
2. тесты правленых тестовых файлов — по имени; имя теста, извлечённое
   скриптом, проверить на пустоту: пустой `-t` запускает файл целиком;
3. тронуты книга посадок, данные стенда, корпус либо любой текст в
   `.claude/tools/` — комментарий, справочник, — тест «составное имя посадки
   и прикрытия стоит только своим объявлением файла» по имени;
4. тронута проза полки — правила, скиллы, справочники, todo — `verify` в
   испытательной посадке: там бюджет доктрины, заголовки критериев, числа в
   прозе, команды с переменной оболочки;
5. тронуты книга, стенд либо механизм посадки — ворота стенда
   `bar-probe --stand-check`.

| Ловушка | Признак | Что делать |
| --- | --- | --- |
| кончилось место на диске | `ENOSPC` в выводе; полный набор падает на корпусе и на тесте словаря | `df -h /` до сборки площадки; песочницы прошлых сессий удалить явными именами; папки прогонов тестов снимаются сами с `4028205` |
| площадка работника не помечена доверенной | в выводе ошибок `claude -p` строка «Ignoring … permissions.allow entries … not been trusted»; `permission_denials` не пуст на командах, которые список посадки разрешает | дать работнику список разрешений семени флагом `--settings` — справка «Сессия-работник»; хуки идут и без него |
| сплошная чистка `/tmp` | среда отказывает в команде даже по слову разработчика | удалять по названным путям |
| посадка не в пустую папку либо внутри другого репозитория | отказ `seat` до любой правки | папка пустая и вне любого репозитория; повторный вызов той же командой на ту же папку обновляет полку |
| пакеты | установка `npm` идёт по сети и медленно | ключ `--packages <папка с пакетами>` берёт их ссылкой, если там стоит каждый пакет манифеста посадки |
| `npm` контейнера ниже связки | корпусный тест знакомого проекта падает отказом «Среда ниже проверенной связки»; испытательная посадка при этом садится | поднять среду загрузчиком посадки `bash .claude/seat/bootstrap.sh` до первого прогона |
| испытательная посадка старше полки | тест по имени проходит, не найдя своего: посадка скопировала полку до правки | после каждой правки полки — команда шага 2.1 и только потом тест |
| имя посадки либо прикрытия встречается в другом файле папки инструмента | тест «составное имя посадки и прикрытия стоит только своим объявлением файла» краснеет на `foreign-corpus.json`, `bar-stand.json` либо на комментарии в `graph.mjs` (`2026-11-07`: обработчик `onOpen` посадки совпал с данными стенда; имя прикрытия попало в комментарий о находке) | новые имена посадок проверить поиском по `.claude/tools/` до записи; в комментариях и справочниках имён посадок и прикрытий не писать — называть форму словами; тест по имени — до полного набора |
| код возврата фонового прогона | уведомление о конце команды показывает код последней команды, а не тестов | писать `echo "exit $?"` в лог и читать код из лога |
| вывод `vitest` в лог | строки появляются только в конце прогона | лог по ходу не опрашивать; ждать уведомления |
| `pkill -f` по шаблону команды | убивает и собственную оболочку: шаблон стоит в её командной строке | останавливать по номеру процесса — например, из файла владельца рядом с папкой прогона |
| режим инструмента внутри песочницы | признак сессии наследуется, и режим ведёт себя как внутри проекта этой сессии | звать `cd <песочница> && env -u CLAUDE_CODE_CHILD_SESSION node .claude/tools/graph.mjs …` |
| счёт расхождений формата | `prettier` без конфига посадки считает по своим умолчаниям | брать `prettier` и его конфиг из папки посадки; сравнивать число до правки и после |
| проза todo и базы | краснеют сверки «Числа в прозе базы», «Ссылки на разделы», «Ссылка на критерий планки несёт его заголовок» и сверка путей | счёт и номер — в обратных кавычках; число прямо перед существительным не ставить (`3.3.3, новым файлом` читается счётом); номер критерия — с заголовком ёлочками, `A1 «Узел отвечает на один вопрос»`, заголовки печатает сама сверка; путь в обратных кавычках — только существующий, а путь мастерской вне `.claude/` (`workshop/`, корневые README) в прозе полки — без кавычек: в испытательной посадке его нет; ссылка на раздел — его точным заголовком без вложенных кавычек; маркеры отложенной работы прописными не писать |
| путь каркаса в прозе полки | корпусный тест красен на каждом знакомом и пустом проекте разом (`25` посадок `2026-11-08`), а `verify` испытательной посадки — код `0`: в ней каркас лежит, и путь вида src/app/… в обратных кавычках ведёт в файл; в проекте корпуса файла нет, и «Пути в обратных кавычках» называет todo полки | путь файла проекта в todo и прозе полки — без обратных кавычек либо словами; после правки todo — корпусный тест по имени одного знакомого проекта до полного набора |
| пометка пропуска CI в теле сообщения | push последнего коммита пачки не запустил `harness-windows`: GitHub снимает запуск, если пометка пропуска стоит в сообщении где угодно, и рассказ о ней в теле тоже снимает | в теле сообщения пометку не называть буквально — «коммиты без запуска CI»; не запустилось — `workflow_dispatch` вручную (`actions_run_trigger`) |
| `claude -p` | ключ `--allowedTools` принимает список и забирает задание, стоящее после него; разрешения из настроек песочницы не действуют | задание — первым словом после `-p`; разрешения — ключом |
| замер покрытия | `NODE_V8_COVERAGE` не видит модулей в воркерах vitest и части дочерних процессов | не использовать; ветки посадки — ручным проходом шага 2.4 |
| `TMPDIR` песочниц не существует | ворота стенда и посадка падают на каждой посадке книги: «временная папка системы недоступна … (ENOENT)» | папку завести до первого вызова: `mkdir -p <папка>` |
| текст новой посадки не проходит ворота стенда | ворота называют посадку: линт `no-magic-numbers`, `restrict-plus-operands`, формат; одна поломка — повтор ворот, а они идут минуты | число в тексте посадки — именованной константой; число в строку — через `String(n)`; каждый текст посадки прогнать `prettier` стенда скриптом до ворот — как в шаге 3.1 прогона `2026-11-07` |
| посадка, которая не нарушение | свод не называет критерий, и промах ложится на суждение, хотя виновата посадка (`2026-11-07`: чистое дописывание в новый массив под `C13`; встроенный `new Intl.DateTimeFormat` под `A15`) | до записи прочитать тело критерия и форму держателя из `bar-hold`: посадка либо в форме, которую держатель видит, — тогда она меряет держатель, — либо в форме «вне держателя» — тогда меряет чтение; форму выбирать нарочно и называть в `why` |
| бюджет доктрины после правки правил | `verify` краснеет на «Доктрина в бюджете» уже после полного набора | `verify` — до полного набора; рост разобрать порядком `CLAUDE.md` мастерской, раздел «Превышение бюджета доктрины разбирается до сокращения», затем поднять `doctrineBudget` |
| команда с переменной оболочки в прозе полки | тест «проза полки не даёт сессии команду с переменной оболочки» краснеет; работник встаёт на отказе среды | в командах правил, скиллов и справочников — без `$?`, `$имя`, `${…}`; значение — выводом отдельного вызова либо однострочником `node -e` в одинарных кавычках |
| две части коммита в одном файле | интерактивного `git add -p` в среде нет | собрать версию файла только с первой частью разовым скриптом, положить её в индекс `git update-index --cacheinfo 100644,<хеш>,<путь>` (хеш — `git hash-object -w <файл>`), прогнать по имени тест этой части на этой версии, затем коммит; вторая часть — обычным `git add` |
| `verify` внутри `seat` при обновлении испытательной посадки | итог «сверка базы красная — без признака сессии» | это признак сессии, а не посадки: `verify` звать отдельно, `env -u CLAUDE_CODE_CHILD_SESSION` |
