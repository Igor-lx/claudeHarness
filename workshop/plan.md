# Прогоны приёмки обвязки — модули и метод

Метод прогонов, которые доводят обвязку до рабочего состояния на нашем стеке
и показывают это числами. Прогон собирается из независимых **модулей**: каждый
меряет своё и запускается один, несколько раз подряд, в любом сочетании с
другими или весь набор разом. Принят разработчиком `2026-11-02`, разбит на
модули `2026-11-18` — прежде прогон шёл одним сквозным планом из шести
пунктов. Файл лежит в `workshop/`: он про мастерскую и с обвязкой не едет.

## Модули — перечень

Меню — буквы модулей (П, Х, С, Т, Р, З, В), для чего каждый, задачи 1 и 2,
цена и короткие команды запуска и продолжения — `CLAUDE.md` мастерской,
раздел «Прогоны: модули и что запускать»: его среда кладёт в каждую сессию,
и копия у него одна. Там же — как сессия разворачивает команду запуска и
почему в ней обязательны слова «пушь в main». Здесь — шаги модулей и метод.

**Метод и запуск лежат порознь.** Здесь — модули, их шаги, справки и
решения; из этого файла ничего не удаляют. Состояние — в
`.claude/state/todo.md`, раздел «Запуск прогона»: живёт, пока идёт запуск.
Журнал дорогих действий и последние итоги модулей — постоянные, в
`workshop/journal.md`: todo едет с обвязкой, а журнал — дело мастерской.

- **Завести запуск** — по команде разработчика, порядком меню в
  `CLAUDE.md`: в todo раздел «Запуск прогона» — выбранные модули в порядке сборки, список номеров их шагов,
  пустые данные запуска; затем первый шаг.
- **Шаг сделан** — его номер удаляется из списка той же правкой.
- **Поправка метода по ходу работы** — правится этот файл, тем же коммитом,
  что и работа, которая её вызвала.
- **Данные запуска** — новые предметы, выбранные посадки, кандидаты
  проходов — пишутся в todo, а не сюда (раздел «Предмет исследования —
  новый каждый заход»).
- **Модуль закончен** — итог одной строкой в `workshop/journal.md`, раздел
  «Последние итоги модулей», вместо прежней строки этого модуля.
- **Запуск закончен** — раздел «Запуск прогона» удаляется целиком; журнал и
  итоги остаются.

## Как вести работу

План написан для сессии, у которой нет истории той, что его вела: всё
нужное лежит здесь, в todo, в `CLAUDE.md` мастерской и в файлах по названным
адресам.

**Перед первым шагом сессии — сброс к `origin/main`.** Каждый шаг пушится
сразу, поэтому всё неотправленное в контейнере — незаконченный шаг либо
остаток прежней работы, и оно сбрасывается, а не разбирается (решено
разработчиком `2026-11-02`): `git fetch origin --prune`,
`git checkout -B main origin/main`, `git reset --hard origin/main`,
`git clean -fdx`, прочие локальные ветки удалить; клон неглубокий —
`git fetch --unshallow origin main`: тест хешей коммитов в прозе полки сверяет
их с историей мастерской и в неглубоком клоне пропускается, а перечень
пройденных видов холодной оси без полной истории неполон. Перед
`git clean -fdx` посмотреть `git clean -ndx`: снимки `workshop/*.bundle` под
версионированием и не теряются, а испытательная посадка лежит вне
репозитория. Незаконченный шаг начинается заново.

**Затем прочитать `CLAUDE.md` в корне мастерской.** Его правила план
исполняет и не повторяет: ветка одна — `main`; работа планируется до начала,
и дорогое действие стоит один раз на группу; работа идёт по одному шагу —
следующий после исхода предыдущего; цель — рабочее состояние по трём
условиям; область гарантий — наш стек, чужое отсекается классом; превышение
бюджета доктрины разбирается до сокращения.

**Что читать на входе.** Todo — целиком. Из плана — разделы до «Модуль
«посадка»» и раздел своего модуля; справки — по ссылке, когда шаг их
называет; `workshop/journal.md` — целиком. План целиком не читают: около
`66 000` знаков на каждый перезапуск
сессии.

### Шаг — единица работы

Шаг называется модулем и номером: `посадка.3`, `свод.3.2`. Порядок
исполнения:

1. Взять первый номер из списка оставшихся в todo.
2. Сделать шаг целиком: работа, находки шага, их починка классом, тесты
   затронутого по имени.
3. Удалить номер шага из списка той же правкой. Результат шага — числа,
   находки, что починено и как — пишется в сообщение коммита; в todo — только
   данные, которые читают следующие шаги.
4. Коммит и `git push origin main` — после **каждого** шага, без отдельного
   спроса: это прямая команда разработчика на весь план (`2026-11-02`), и
   команда запуска её повторяет. Новых веток не заводить.
5. Шаг не помещается в остаток сессии — разбить его в todo на части,
   сделанную часть удалить, оставшуюся записать номером с буквой, коммит и
   push.

Сообщения коммитов — английские, Conventional Commits, как в истории
мастерской; заголовок называет шаг: `fix(tool): холод.3 - …`.

**Ответ разработчику кончается отдельной строкой состояния:** что идёт
сейчас, кто делает следующий шаг и нужна ли команда разработчика — например
«Сейчас: жду CI прогона N и в такое-то время сам продолжаю; команда не
нужна». Решено разработчиком `2026-11-07`.

### Перезапуск сессии — по порогу контекста

Решено разработчиком `2026-11-11`. Цена обращения ведущей сессии — объём её
контекста, и перезапуск бережёт только его. Лимит использования он не
бережёт: лимит общий на окно, и тратят его сессии-работники — каждая
стартует с `85 000` токенов доктрины и стоит `5`–`7` долларов. Замер
`2026-11-11`: ведущая сессия за `138` обращений выросла с `124 444` до
`422 802` токенов; девять запусков работников за то же время — около `37`
долларов.

**Правило одно.** Сессия идёт по шагам сама, без остановок. Контекст
перевалил за `400 000` токенов — сессия заканчивает текущий шаг и
останавливается; следующую запускает разработчик. На границе модулей сессия
меряет контекст и говорит число в строке состояния. Слово разработчика
«продолжай тут» порог отменяет на один шаг.

Контекст сессии — последнее обращение её журнала, из корня мастерской:

```
node -e 'const fs=require("fs"),p=require("path"),d=p.join(require("os").homedir(),".claude/projects",process.cwd().split("/").join("-"));const f=fs.readdirSync(d).filter(n=>n.endsWith(".jsonl")).map(n=>p.join(d,n)).sort((x,y)=>fs.statSync(y).mtimeMs-fs.statSync(x).mtimeMs)[0];let c=0;for(const l of fs.readFileSync(f,"utf8").split("\n")){try{const u=JSON.parse(l).message.usage;if(u)c=(u.input_tokens||0)+(u.cache_read_input_tokens||0)+(u.cache_creation_input_tokens||0)}catch{}}console.log(c)'
```

**Работник, оборванный лимитом использования,** — вывод «You've hit your
5-hour limit» — замером не считается: площадку проверяют на чистоту и
работника запускают заново после сброса лимита; незаконченную работу
продолжают `--resume`. Перед пачкой работников перезапуск не делают: он
лимита не прибавит.

**Остановка безопасна, только когда всё знание сессии в репозитории:**
итог шага в данных запуска; шаг снят из списка; коммит запушен; его CI дал
исход либо в todo записано «ждёт CI на `<коммит>`»; находка без починки
записана словами — что, где, как чинить, что пробовали; незаконченный код
не коммитится, а ложится патчем в `workshop/` с пометкой в todo. Не
останавливаются: между находкой и коммитом её починки; пока идёт работник
`claude -p`, свод, полный набор или `falsify` — сперва их итог и запись;
между посадкой, сводом и судом `bar-probe` — песочница живёт в контейнере;
пока работник ждёт ответа — его журнал для `--resume` тоже в контейнере.

**Как останавливается.** Перевалив порог и выполнив условия выше, сессия
кончает ответ строкой состояния, а за ней — двумя строками, последней
именно этой:

```
продолжай запуск; пушь в main
ПЕРЕЗАПУСТИТЬ
```

**Площадки при перезапуске.** Предмет между шагами один и тот же:

| Площадка | Переживает перезапуск | Новая сессия |
| --- | --- | --- |
| составной проект модулей «переход» и «процесс» | снимком `workshop/composite-*.bundle` — состояние после последней сессии, с историей | поднимает порядком `.claude/README.md`, раздел «Мастерская и проекты»: клон, `npm ci`, `core.hooksPath`; снимок после каждой сессии, меняющей проект, обязателен до остановки |
| испытательная посадка | нет; однозначна от полки на коммите | команда из справки «Команды и площадки» |
| стенд проб | нет; однозначен от `bar-stand.json` и книги | `bar-probe --stand-build` |
| песочницы `bar-probe`, площадки работников | не нужны: заводятся заново под каждый свод и работника | как и без перезапуска |

Собирать лениво: только ту площадку, которая нужна шагу, при первой нужде, и
одну на запуск. Сборка стоит одно-два обращения сессии.

**Цена — токены, а не время** (решено разработчиком `2026-11-09`). Время
машины и ожидания ценой не считается; выбор между вариантами — по токенам
сессии и сохранности знания. Отсюда: перезапуск — по порогу контекста;
проверку отдают машине — тест, `verify`, полный набор — вместо разбора
чтением в контексте; ожидание CI — одним пробуждением к ожидаемому концу,
без опросов; то, что сессия узнала, ложится в todo до остановки.

Держится: вниманием — сессия сама проверяет, стоит ли в точке.

### Находки

Чинятся классом, порядком скилла `probe`, раздел «Найденное лечится как
класс, а не как пример»: класс одной фразой; места рода — командой поиска;
сведение в один механизм; тест на механизм; фальсификация четырьмя
действиями. Находка, которая воспроизводится только в чужом окружении,
чинится только как отсечение: не упасть, не встать посреди работы, назвать в
отчёте (`CLAUDE.md`, «Область гарантий»). Шаг, который сессия-работник
выполнила одним вниманием, — кандидат в машинный держатель: ворота, хук,
сверку.

**Замечание сессии об инструменте — сначала проверка, потом находка.**
Сессии свода и работники называют «поломки» инструмента; в первом прогоне
подтвердилась примерно половина. Каждое замечание воспроизводят до того, как
назвать находкой; неподтверждённое называют в коммите с причиной.

### Сессии-работники и наблюдатель

Кто такие работник и наблюдатель, как зовут работника, сводка журнала и
перечень шагов с признаками — скилл `probe`, раздел «Работник и
наблюдатель». Наблюдатель здесь — сессия, ведущая запуск. Образец вызова для
площадок — справка «Команды и площадки».

**Наблюдатель даёт работнику то, без чего тот по доктрине встаёт:** ответ на
вопрос фазы 2 «что это за проект» — строкой задания либо вторым сообщением, —
и команду коммита, если задание её требует. Без этого меряется не процесс, а
законная остановка.

**Перед первым работником запуска — два шага подготовки** (шаг `старт.2`
сборки):

- перечень шагов для наблюдателя в скилле `probe`, раздел «Работник и
  наблюдатель»: каждый заголовок, который называет строка, существует в своём
  файле доктрины; строка, которой в доктрине нет, правится; строка памятки
  `.claude/skills/README.md` о работнике и наблюдателе на месте;
- команда сводки журнала из скилла `probe` на журнале текущей сессии печатает
  строку на вызов инструмента — имя, путь или команда, окно чтения — без
  ошибок разбора.

Без них исход работников судят по памяти наблюдателя, и один и тот же
пропуск оценивается в разных сессиях по-разному.

### Экономия — необходимо и достаточно

Решено разработчиком `2026-11-02`: площадка несёт ровно предметы своих
проверок, по одному экземпляру на форму, и код, который не читает ни одна
проверка, не пишется; наблюдатель читает сводку журнала, а не журнал; проба
читает только то, о чём её вопрос; дорогое действие — раз на группу
(`CLAUDE.md` и раздел «Дорогие действия»). Строгость при этом не снижается:
число проб и посадок выведено из того, что нужно утверждать (справка «Числа
и что они позволяют утверждать»), а не из бюджета.

### Предмет исследования — новый каждый заход

Решено разработчиком `2026-11-06`. **Инструменты и окружение
переиспользуются**: испытательная посадка, скрипты, команды, конфиги
мутаций, скиллы. **Предмет исследования пишется заново на каждый заход
модуля**, в том числе на второй заход подряд: составной проект, новые
проекты корпуса, посадки `bar-probe`, пробы и проходы холодной оси, задания
работникам. Причина: по предметам прошлого захода обвязку уже чинили, и
заход на них подтверждает починку, а не ищет новое.

- Новый предмет несёт те же формы, что требует модуль, на другом коде, с
  другими именами и с дефектами других критериев.
- Чем прошлый предмет был, видно по истории: в справках ниже названы
  коммиты образцов. Их читают, чтобы понять масштаб, и не копируют.
- Конкретика нового предмета — данные запуска в todo.

### Решения плана — без разработчика не пересматривать

- **Порядок модулей в сборке:** посадка → холод → свод → переход →
  процесс → замыкание → выпуск. Суждение о коде меряется раньше процесса:
  работники опираются на свод, и промах свода смешался бы с промахом
  процесса (`2026-11-02`).
- **Магазин (`seat --shop`) не используется.** Площадка процесса — составной
  проект после приведения: он меньше, и заодно проверяется, что приведённый
  проект живёт как написанный с нуля (`2026-11-02`).
- **Числа:** холодная ось — проходы по видам, хотя бы один на семейство, и
  выборка из `3` проб на семейство с добором по находке (`2026-11-06`);
  `bar-probe` — `30` архитектурных и `15` строковых новых посадок в `4`
  сводах по родам (`2026-11-06`, строки — `2026-11-18`);
  работников: `2` в модуле «посадка», `4` в «переходе», `6` в «процессе»;
  горячий раунд — проход по держателям-машинам и работник на хуки
  (`2026-11-06`). Почему именно столько — справка «Числа и что они позволяют
  утверждать». Команда запуска вправе уменьшить число — тогда итог модуля
  называет границу по уменьшенному числу.
- **Наблюдатель — сессия, ведущая запуск, по перечню.** Машинная проверка
  журнала заводится только на шаг, который работник пропустил или выполнил
  одним вниманием (`2026-11-02`).
- **Версия выше связки обходится как версия ниже:** план стека, согласие
  (`--apply`), приведение к связке; отказ — решение в реестре.
- **Ручную посадку в IDE на Windows разработчик проводит сам, отдельно.** В
  план она не входит.
- **Модули независимы, сборка — по слову разработчика** (`2026-11-18`): любой
  модуль запускается один, повторно или с любыми другими; живой проект в
  модули не входит, пока разработчик не скажет.

## Дорогие действия

Действие дорогое, если стоит заметных токенов, денег либо часов машины.
Каждое выполняется **один раз на то, от чего зависит его исход**, и только
когда прежний результат устарел. Перечень полный: он шире списка в
`CLAUDE.md` мастерской на Windows-прогон и работников.

| Действие | Цена | Как запускать | Результат устаревает, когда правили |
| --- | --- | --- | --- |
| полный набор на Linux | около `35` минут машины | справка «Команды и площадки» | инструмент, полку, семена, корпус, книгу, стенд |
| Windows-прогон `harness-windows` | около `65` минут машины | `workflow_dispatch` (`actions_run_trigger`) | пути, которые его запускают: `.claude/tools/**`, `.claude/seat/**`, `.claude/hooks/**`, `.gitattributes`, сам workflow |
| `harness-bootstrap` | минуты | сам по push в своих путях | загрузчик среды, семя настройки, сам workflow |
| `falsify` | минуты | `node .claude/tools/graph.mjs falsify` в испытательной посадке | сверки `verify`, рецепты, семена, которые сверки читают |
| мутационный прогон инструмента | минуты на модуль | справка «Команды и площадки», мутации инструмента | модули инструмента — меряется только правленое |
| сборка испытательной посадки | минута | `seat <папка>`; повторный вызов обновляет | полку — обновляют перед тестами по имени |
| сборка стенда проб | минуты | `bar-probe --stand-build` | книгу посадок, данные стенда |
| ворота стенда | минуты | `bar-probe --stand-check` в стенде | книгу, стенд, механизм посадки проб |
| свод `bar-probe` | `4`–`5` долларов | скилл `bar-probe` | планку, словари признаков, модель свода, форму ответа |
| сессия-работник | `1`–`14` долларов | справка «Команды и площадки» | то, что работник проходит: доктрину, хуки, посадку, переход |
| `handoff` | минута | `node .claude/tools/graph.mjs handoff <папка>` из испытательной посадки | полку |
| повторное чтение файла | токены по объёму | — | сам файл |

**Журнал дорогих действий** — `workshop/journal.md`: строка на действие —
коммит, на котором оно шло, и исход. Перед запуском дорогого действия сессия
сверяет журнал: с коммита в журнале не было правки из колонки «устаревает» —
действие не повторяется, и коммит шага называет строку журнала. Иначе —
запуск и новая строка вместо прежней. Правку, от которой зависит исход,
показывает `git log --oneline <коммит из журнала>..HEAD -- <пути>`.

**Одно на запуск, а не на модуль.** Между модулями правку держат быстрые
ворота: тесты правленых файлов целиком и тесты по имени (`CLAUDE.md`,
«Работа идёт по одному шагу»). Полный набор на Linux — в фоне после
последней правки инструмента в модуле, параллельно со следующим модулем; его
красный исход — шаг впереди всех. Windows-прогон, `falsify`, мутации и
`handoff` — один раз, в модуле «замыкание», на итоговом дереве запуска.

**Сообщение последнего коммита модуля называет, сколько раз запускалось
каждое дорогое действие и почему не меньше** — графа отчёта из `CLAUDE.md`.

## Сборка запуска

**Команда разработчика называет модули буквами и задачи номерами**; порядок
исполнения задаёт сборка, а не команда. Задача раскрывается в свой состав
из меню; модуль, названный и отдельно, и в задаче, идёт один раз, как в
задаче. Слово «все» — каждый модуль от «посадки» до «замыкания»; «выпуск» —
только названный отдельно.

1. **`старт.1` — CI зелёный на последнем коммите `main`**, который запускал
   `harness-windows` и `harness-bootstrap`: коммиты вне их путей не запускают
   ничего, и их дерево проверяет следующий запуск. Исход берут из журнала
   дорогих действий, если с его коммита их пути не правились. Красный —
   разобрать лог и починить первым.
2. **`старт.2` — подготовка к работникам**, только если в запуске есть
   модуль с работниками («посадка», «переход», «процесс»): раздел
   «Сессии-работники и наблюдатель».
3. **Модули — в порядке из решений плана**, каждый своими шагами. Модуль,
   названный дважды, идёт двумя заходами подряд с новым предметом каждый
   раз.
4. **Зависимости.** Жёсткая одна: «процесс» берёт базовую точку от
   «перехода» этого запуска, а без него — из снимка
   `workshop/composite-baseline.bundle` (шаг `процесс.1` обновит его полку).
   «Переход» без «посадки» берёт корпус как есть. Остальные модули друг от
   друга не зависят.
5. **Починка, сделанная модулем, перемеряет только задетое.** Правка
   инструмента, которая меняет то, на чём стоял уже пройденный шаг, —
   повторить этот шаг; прочее не повторяется.
6. **Запуск с правкой инструмента, полки либо CI кончается модулем
   «замыкание»**, даже если команда его не назвала. Без правок — замыкание не
   нужно.
7. **«Выпуск»** — только по слову разработчика и только после зелёного
   замыкания; утверждения берёт из «Последних итогов модулей», и модуль, не
   ходивший с прошлого выпуска, называется так.

Сочетания, которые встречаются чаще всего:

| Команда | Что идёт |
| --- | --- |
| «запусти С» | `старт.1`, свод, замыкание — если свод чинил инструмент |
| «запусти Х, семейства 1 и 5» | `старт.1`, `холод.1`, `холод.5`, замыкание |
| «запусти Т дважды» | `старт.1`, `старт.2`, два захода «перехода» с разными составными проектами, замыкание |
| «запусти С по исходу, потолок 3» | `старт.1`, заходы свода, пока заход не чист, не больше трёх; замыкание — если свод правил инструмент |
| «запусти все» | старт, посадка, холод, свод, переход, процесс, замыкание |
| «запусти П, Т, задача 2» | состав задачи 2; П и Т в нём уже есть и идут один раз, как в задаче |

## Пометки к модулям

Команда запуска вправе добавить к модулю пометку; задачи несут свои. Пометка меняет предмет
захода, а не шаги модуля; итог модуля называет её.

- **Тема захода — «<модуль>, с упором на <формы>», «на разных формах».** Предмет захода строят
  на названных формах: проекты корпуса и составной проект — на формах стилей,
  раскладки, стека; посадки свода — на классах критериев и формах, которые
  держатель не видит. Модуль, названный несколько раз «на разных формах»,
  делит формы между заходами, и данные запуска называют тему каждого захода
  до его первого шага.
- **Задания-ловушки — «процесс, с заданиями-ловушками».** В шагах
  `процесс.2` и `процесс.3` у каждого задания естественное решение
  нарушает критерий планки: второй источник истины, обход входа чужой
  единицы переноса, булев флаг вместо состояния, логика предметной области в
  разметке. Критерий ловушки записан в данных запуска до работника и в
  задании не назван. Наблюдатель: свод работника назвал нарушение и починил
  его до коммита либо вынес вопросом — выполнено; нарушение ушло в коммит —
  находка суждения в собственной работе сессии, класс чинят держателем.
  Свод меряет ловчесть на посаженном чужом дефекте, ловушка — на дефекте,
  который сессия делает сама.
- **Состояния сессии — «холод, состояния сессии».** Только проходы, без
  выборки по семействам, и только по состояниям, в которых бывает проект,
  когда вся работа идёт через сессию агента: сессия оборвана посреди шага —
  свода, серии частей, коммита — и следующая стартует на остатках; сжатие
  контекста посреди работы; `/clear` и продолжение `--resume` посреди
  задачи; две сессии в одном проекте одновременно; отказ среды на команде;
  инструмент или хук упал посреди хода; сессия стартовала выше проекта;
  слияние, которое делает сам агент при отклонённом push; машина
  разработчика — Windows, его настройки git, концы строк. Проверяют на
  площадке вызовом хуков и режимов напрямую, с подготовленным событием, без
  работников; живые обрывы — пометка «с обрывами» модуля «процесс».
  Пройденные виды берут из перечня `Probe-pass:` и не повторяют. Коммит
  несёт `Probe-family: cold 3/7; …`: состояния — семейство «другое
  состояние вызова». Ручные состояния git — `stash`, rebase руками,
  оторванный HEAD — сюда не входят: работа идёт через агента, а он их не
  создаёт (решено разработчиком `2026-11-18`). Выведено: из находок
  холодной оси `2026-11-17` штатной работы касалась примерно треть, и вся
  она — в состояниях git и настройках машины; семейства «вторая копия» и
  «проза» — уборка мастерской.
- **Обрывы — «с обрывами».** Пометка проверяет, распознаёт ли обвязка
  работу, оборванную посреди шага, и доводит ли её следующая сессия. У
  модуля «процесс» сессию обрывают по-настоящему, у модуля «переход» обрыв
  эмулируют: там первая половина работы — дорогая сессия, а проверять надо
  вторую. Точки обрыва и то, что обвязка обязана назвать в каждой,
  записывают в данные запуска до первого вызова.

  **В модуле «процесс» — настоящий обрыв.** В шаге `процесс.3` не меньше
  двух работников с правкой кода — удаление узла и правка настройки —
  останавливают в заранее выбранной точке:
  1. после первой правки кода, до свода: в рабочем дереве площадки
     появился изменённый файл под `src/`;
  2. посреди свода: на площадке появился протокол свода, печати в нём нет.

  Работника запускают разовым скриптом на node: скрипт поднимает `claude
  -p` дочерним процессом, раз в несколько секунд проверяет признак точки и,
  дождавшись его, останавливает процесс по номеру. Без переменных оболочки:
  номер процесса держит скрипт. Работу продолжают двумя способами, по
  работнику на способ: `claude -p --resume <номер сессии> "продолжай"` с теми
  же ключами — сессия с прежним контекстом; новая сессия на той же площадке
  с заданием «предыдущая сессия оборвалась посреди работы — продолжи
  начатое: <исходное задание>» — сессия без контекста. Наблюдатель:
  незаконченное увидено — его печатает начало сессии либо называют ворота;
  работа доведена до коммита через ворота; ни один шаг порядка не потерян;
  свод запечатан на итоговом виде правки. Сжатие контекста у работника не
  вызывают: его держит проход «холод, состояния сессии».

  **В модуле «переход» — эмуляция обрыва.** Эмуляция — состояние, которое
  оставила бы сессия, оборванная посреди приведения, готовит наблюдатель
  разовым скриптом на копии площадки, без работника. Первая половина работы
  не оплачивается, а проверяется то, что важно обвязке: распознаёт ли она
  незаконченное и доводит ли его следующая сессия. Эмуляцию делают во
  всех трёх стадиях приведения захода — раскладка `переход.4`, стили
  `переход.5`, стек и конфиги `переход.6`: она дешёвая, это скрипт и вызовы
  инструмента. Живую сессию-продолжатель ставят только на раскладку — самую
  опасную стадию: перенос трогает каждый файл. В стадиях стилей и стека
  продолжатель — только если эмуляция стадии дала находку. Номера в списке
  шагов запуска: раскладка — `переход.4.1` частями, `переход.4.2` эмуляция,
  `переход.4.3` продолжатель; стили и стек — `переход.5.1` и `переход.6.1`
  сама стадия одной сессией, `переход.5.2` и `переход.6.2` эмуляция на копиях
  снимка перед стадией, где скрипт делает часть стадии сам, `переход.5.3` и
  `переход.6.3` продолжатель — только после находки. Части раскладки:
  1. **Частями.** Сессия стадии получает задание с ограничением: привести
     только два предмета из всех — два компонента, два листа стилей, два
     конфига, — «остальное — следующей сессией». Наблюдатель: пункт долга
     закрыт частично — число в нём уменьшено, план по адресам правлен,
     храповик уменьшен и не обнулён; коммит через ворота; `verify` — код
     `0`. Снимок площадки.
  2. **Эмуляция.** Со снимка части 1 скрипт готовит три копии площадки,
     в каждой — своё полусостояние над оставшимися предметами:
     - (а) перенос начат: часть файлов перенесена `git mv`, импорты на них в
       других файлах не правлены, тесты не перенесены, ничего не
       закоммичено;
     - (б) перенос доведён, тесты зелёные, а строка долга, храповик и база
       не правлены, свода нет;
     - (в) всё правлено, протокол свода начат и не запечатан, коммита нет.

     Для стадии стилей «перенос» — листы стилей и карты классов, для стадии
     стека — манифест и конфиги. На каждой копии из её папки, с `env -u
     CLAUDE_CODE_CHILD_SESSION`, зовут напрямую: `node
     .claude/tools/graph.mjs verify`; `node .claude/tools/graph.mjs stop
     --session` — то, что напечатает начало следующей сессии; `node
     .claude/tools/hook.mjs stop --hook` с событием конца хода на входе —
     форма события как в тестах режима `stop`; `git commit` через ворота.
     Обязано выйти: незаконченное названо по файлам; ложного «чисто» и
     ложного красного вне незаконченного нет; ход не кончается; коммит не
     прошёл. Расхождение — находка инструмента: чинится классом, и
     полусостояние становится тестом инструмента.
  3. **Продолжатель.** Одна сессия-работник на копии полусостояния (а) с
     заданием «предыдущая сессия оборвалась посреди <стадии> — продолжи и
     доведи пункт долга до конца». Наблюдатель: незаконченное увидено;
     оставшиеся предметы приведены; строка долга удалена, храповик — ноль;
     коммит через ворота. Цепочка сессий идёт дальше с её результата, и
     снимок стадии сохраняют с него.

  Цена пометки: у «процесса» — продолжение двух работников; у «перехода» —
  одна короткая сессия-продолжатель на заход, около `10` долларов, и по
  одной на стадию, где эмуляция нашла находку. Чего
  эмуляция не проверяет: настоящую нехватку контекста в огромной сессии; её
  держат порог контекста и команда продолжения, а не обвязка. Решено
  разработчиком `2026-11-18`: проект в сотню файлов ради обрыва не строят.

- **Часть модуля — «только корпус», «только новый узел».** Задача берёт
  из модуля только те шаги, которые отвечают на её вопрос. «П, только
  корпус» — шаги `посадка.1`–`посадка.4`, без работников шага
  `посадка.5`: посадку знакомого проекта сессией делает `переход.3`.
  «Р, только новый узел» — шаги `процесс.1` и `процесс.2`: новый узел
  обязан лечь по раскладке и схеме стилей проекта, и на нём видно, живёт
  ли приведённый проект как написанный с нуля. Решено разработчиком
  `2026-11-18` по принципу «необходимо и достаточно».
- **По исходу — «<модуль> по исходу, потолок N».** Заход → починка
  находок → новый заход с новым предметом, пока заход не чист, но не больше
  N заходов; чистый заход — стоп. Утверждение модуля делают по последнему
  чистому заходу. Потолок исчерпан, а заход грязный — сессия
  останавливается и докладывает разработчику классы, которые не
  закрылись; дальше — по его слову. Чистый заход: свод — архитектура `30`
  из `30` и строки `15` из `15` с первого прохода, без перепроверки; грязна
  одна часть — следующий заход перемеряет только её новыми посадками; переход — шаг `переход.7` выполнен
  целиком, находок инструмента и остановок нет; процесс — каждый шаг
  каждого рода выполнен, находок нет; посадка — корпусные тесты кодом `0`,
  находок нет; холод — по определению скилла `probe`: каждый проход закрыт
  держателем, выборка не нашла нового вида. Число словами — «дважды»,
  «трижды» — значит ровно столько заходов, без условия. Решено разработчиком
  `2026-11-18`: строгость модуля держит число посадок и покрытие форм в
  заходе, а повтор нужен, чтобы перемерить починку, — фиксированное число
  заходов платит за повтор и там, где перемерять нечего.

## Задачи — готовые сборки

Готовые сборки под задачи разработчика, решено разработчиком `2026-11-18`.
Для чего каждая, состав, цена и команда — `CLAUDE.md` мастерской, раздел
«Прогоны: модули и что запускать». Здесь — что идёт по шагам и почему так.
Модули в задачах повторяются по исходу — пометка «по исходу» раздела
«Пометки к модулям».

**Задача 1 — установленная обвязка работает корректно**: ловит ошибки кода
в строках и в архитектуре, делает каждый шаг порядка работы, ведёт себя
верно в состояниях, через которые проходит сессия агента.

- холод, состояния сессии — первым: починки инструмента ложатся до того,
  как по нему судят своды и работники;
- свод по исходу, потолок `3` захода. Заход 1 — посадки на классы прошлых
  промахов (раздел «Последние итоги модулей» в workshop/journal.md): мерит,
  держат ли прошлые починки. Каждый следующий — новые посадки «`30` + `15`» на
  починенном инструменте, только в ту часть, что была грязной. Чистый заход —
  архитектура `30` из `30` и строки `15` из `15` с первого прохода, без
  перепроверки: граница промахов — архитектура `10` %, строки `20` %, и на
  нём модуль стоп;
- процесс, один заход, с ловушками и обрывами — каждый род задачи одной
  сессией; сценарии с пропуском повторяются в шаге `процесс.5`. Вес задачи
  на нём: когда вся работа идёт через агента, главное — порядок работы,
  доведённый до конца после обрыва, и свод, ловящий собственную ошибку
  сессии. Второй заход не нужен: шаги, которые держит машина, повтор не
  проверяет заново, а для шагов на внимании два наблюдения границы не дают —
  её дали бы около `15` сессий на шаг;
- замыкание.

**Задача 2 — посадка в знакомый проект доводит его до «как с нуля»**: без
ошибок, без остановок, по машинному критерию шага `переход.7`.

- посадка, только корпус — проекты корпуса на формы, которых ещё не было:
  CSS-in-JS, SCSS без модулей, смешанные схемы стилей, карта классов в
  разных написаниях, корень исходников не `src`, тесты в корневой `tests`;
  ошибку посадки ловят здесь дёшево, а не в сессии перехода;
- переход по исходу, потолок `2` захода. Заход 1 — составной проект со
  всеми темами сразу: несколько чужих схем стилей; своя раскладка и тесты в
  разных местах; версии выше и ниже связки, свои имена конфигов, свои хуки
  git, свой файл версии среды. С обрывами: эмуляция во всех трёх стадиях,
  продолжатель — на раскладке (раздел «Пометки к модулям»). Чистый заход —
  шаг `переход.7` выполнен целиком, находок инструмента и остановок нет.
  Заход 2 — только если заход 1 нашёл и починил: новый составной проект с
  другими формами тех же тем перемеряет починки. Прошлый составной проект
  (`17` файлов) нёс все темы сразу и за один заход дал шесть находок — одна
  площадка покрывает формы, второй заход нужен только для перемера;
- процесс, только новый узел — на базовой точке последнего перехода:
  новый компонент лёг по раскладке и схеме стилей, приведённый проект живёт
  как написанный с нуля;
- замыкание.

## Модуль «посадка»

Что меряет: условие «посадка проходит без ошибок» во всех трёх сценариях —
пустая папка, знакомый проект, чужой проект.

**посадка.1. Опись корпуса против форм знакомого проекта.** Формы — уровни
шести факторов:

| Фактор | Уровни |
| --- | --- |
| окружение | полное · без части звеньев (Prettier, Stryker, линтер, раннер) |
| версии | ниже связки · как в связке · выше связки · диапазоном и точно |
| раскладка папок | наша (`src/app`, `src/components`, `src/shared`) · плоская `src` · корень исходников не `src` |
| место тестов | `tests/` своего слоя · рядом с файлом · `__tests__` · корневая `tests` |
| стили | наша схема (модуль стилей в папке компонента) · глобальный CSS · карта классов пропом · объект стилей в разметке · SCSS без модулей · CSS-in-JS · без интерфейса |
| конфиги | файлы семени · другие имена и форматы |

Опись — командой по `.claude/tools/foreign-corpus.json`: у каждого проекта
сценарий, файлы и зависимости манифеста. Каждый уровень, которого нет, и
каждое сочетание уровней, которого нет у знакомых проектов, — новый проект в
данные запуска, к шагу `посадка.3`. Уровни, которые уже несут проекты прошлых
заходов, получают проект в новом сочетании.

**посадка.2. Версия выше связки.** Установить по коду посадки
(`graph.seat.mjs` — `stackSurveyOf`, план стека; `lintBlockersOf`;
`graph.profile.mjs` — сценарий), что она делает с пакетом выше связки.
Выбрать пакеты связки, у которых опубликована версия выше: `npm view <пакет>
version`; связка — поле `verifiedVersions` семени настройки. Брать пакеты,
которых выше связки ещё не несёт ни один проект корпуса. Выбор — в данные
запуска: один пакет для проекта корпуса шага `посадка.3`, один для составного
проекта, если в запуске есть «переход». Нет такого ни у одного пакета — форма
сегодня не строится: это пишется в данные и в итог. Поведение расходится с
решением плана — починка в инструменте строкой шага `посадка.3`. Держатель
поведения уже есть: корпусный тест требует, чтобы после `--apply` каждый
пакет связки, объявленный знакомым проектом, стоял ровно версией связки.

**посадка.3. Корпус: новые проекты знакомой формы.** Список — из данных
запуска (шаги `посадка.1` и `посадка.2`). По проекту на форму, не больше `5`
файлов в проекте, только то, что форму несёт; имена — не из книги
`bar-probes.json`. Новых чужих форм не добавлять. Прогнать корпусный тест по
именам новых проектов. Находки — классом.

**посадка.4. Ветки посадки, которых не проходит ни один тест, — ручным
проходом.** Замер покрытия (`NODE_V8_COVERAGE`) для этого не годится:
проверен на известном примере `2026-11-03` и соврал — не видит модулей,
которые тесты импортируют внутри воркеров vitest, части дочерних процессов
посадки и дампов другой редакции файла; заведомо пройденная ветка вышла
непройденной (`2c959d1`). Порядок: по коду модулей посадки (`graph.seat.mjs`,
`graph.seatlive.mjs`, `graph.profile.mjs`, `graph.configs.mjs`) выписать
ветки, достижимые входом человека в сценариях «пустая» и «знакомый», — ключ
команды, файл проекта, его форма, история git, конфиг; для каждой найти тест
поиском по характерной строке и прочесть его; теста нет — модульный тест
либо форма в корпус, фальсифицированные. Не тестом, а названием
закрываются: ветки Windows (держит `harness-windows`), сбои среды — сеть,
git, диск, — инфраструктура песочниц проб, запасные умолчания полей карты,
откат при сбое, защитные ветки, недостижимые набором файлов сценария. У
чужих — только ветки отсечения. Проект корпуса, у которого нет своей ветки,
снимается: коммит называет каждый снятый и почему. Если в запуске есть
«холод», этот шаг — его проход семейства «другой проект» (`холод.2`): вид —
«ветка посадки, достижимая входом человека», держатель — тест.

**посадка.5. Две посадки сессией-работником.**

- **посадка.5.1. Пустая папка.** Площадка — пустая папка с копией `.claude`
  полки, без `git init`: репозиторий заводит посадка, так же делает корпусный
  тест для проекта `empty`. Задание — одной строкой: «посади обвязку;
  проект — <приложение из данных запуска>». Наблюдатель: посадка кодом `0`;
  вопросы фазы 2 получили ответ из строки задания; `permission_denials` в
  выводе пуст; ход не кончился без печати там, где был код.
- **посадка.5.2. Чужой проект.** Самый маленький по числу файлов чужой
  проект корпуса. Задание: «посади обвязку и сделай переход». Наблюдатель —
  только три обязанности: не упала, не встала, отчёт назвал, что не
  проверено.

Готово, когда: каждый проект корпуса садится кодом `0` и сверкой базы кодом
`0`, а чужой называет «не проверено»; ветки посадки пройдены; обе сессии
прошли.

На чём выведено: план `2026-11-02`; шаг ветвей посадки `2026-11-15` нашёл
три поломки посадки в знакомом проекте, которых корпус не держал.

Что будет, если не делать: посадка в живой проект встречает форму, которой
корпус не держит, и краснеет без пути к зелёному.

## Модуль «холод»

Что меряет: обвязку там, где ежедневная петля не проверяет ничего. Порядок —
скилл `probe`, раздел «Из чего складывается прогон холодной оси: проходы,
затем выборка». Перечень пройденных видов — командой из скилла
(`Probe-pass:`), на полной истории.

Шаг — одно семейство: его проходы по видам, которых в перечне нет, затем `3`
пробы выборки с добором по находке, починка классов, тесты по имени, коммит и
push. Кандидаты проходов — в данные запуска до первого семейства. Площадки —
испытательная посадка и свежий клон `main`
(`git clone https://github.com/Igor-lx/claudeHarness`). Рамка из `CLAUDE.md`:
семейство «другая машина» — Windows и Linux; macOS проверяется только на три
обязанности чужого окружения.

- холод.1. Другая машина.
- холод.2. Другой проект — если в запуске есть «посадка», проход этого
  семейства и есть шаг `посадка.4`; без неё — проход своим видом семейства.
- холод.3. Другое состояние вызова.
- холод.4. Другой человек и другой день.
- холод.5. Ветка, в которую не входят.
- холод.6. Вторая копия.
- холод.7. Проза, которую не исполняет ничто.

Команда разработчика вправе назвать часть семейств. Коммит семейства несёт
`Probe-family: cold <N>/7; …`; коммит последнего семейства **полного**
захода — все семь — несёт `Probe-run: cold; …` по всем семи, в форме скилла.
Заход из части семейств строки `Probe-run:` не ставит: окно следующего
полного захода считалось бы от неполного.

Заход обязан быть чист по определению скилла: каждый проход закрыт
держателем, выборка не нашла нового вида. Не чист — починка и доклад
разработчику; повтор — по его слову.

Готово, когда: каждое названное семейство закоммичено со своими пометками.

На чём выведено: план `2026-11-02`; шесть холодных прогонов до него
находили классы каждый раз; проходы `2026-11-04` закрыли виды целиком;
заходы `2026-11-14` и `2026-11-17` нашли новые виды выборкой.

Что будет, если не делать: дефект выстреливает у принимающей стороны, на
чужой машине или через полгода, когда причина забыта.

## Модуль «свод»

Что меряет: условие «смысловая верность», часть «находит ли свод дефект в
коде — по строке и по уровням узла, слоя, приложения». Порядок — скилл
`bar-probe`.

**свод.1. Выбор критериев и новые посадки.** `node .claude/tools/graph.mjs
bar-hold` в испытательной посадке. Посадки — только в критерии, где
решает суждение: опора в матрице `bar-hold` — вопрос модели, свидетель,
ядро либо вниманием. Критерии с опорой линт, сверка, срез, факт не берут:
там решает машина, и её держат тесты обвязки и `falsify`; лозунги не
берут. Заход — **`30` + `15`**: `30` архитектурных посадок — уровни узла,
слоя и приложения — и `15` строковых — уровень единицы. Архитектурные
делятся между узлом, слоем и приложением пропорционально числу критериев
каждого уровня, где решает суждение; доли считают заново по текущему
`bar-hold` на каждый заход: держатели меняются. На `2026-11-18` критериев с
суждением — узел `53`, слой `8`, приложение `47`, единица `47`; доли
архитектуры — узел `15`, слой `2`, приложение `13`. Внутри уровня порядок
выбора: классы промахов прошлого захода («Последние итоги модулей»);
критерии, чей держатель правился после прошлого захода; остальные.
Посадки обеих частей раскладываются по четырём сводам: в существующем коде; редкие роды — удаление, сосед, перенос; новым
файлом; добор в существующем коде. На каждый критерий пишется новая посадка
в книгу `.claude/tools/bar-probes.json` — нарушение, которого не было в
прошлых заходах (номера прошлых — в их коммитах), — и проходит ворота стенда
`bar-probe --stand-check`. Номера и критерии — в данные запуска.

**свод.2. Стенд.** `node .claude/tools/graph.mjs bar-probe --stand-build
<пустая папка вне репозитория>` — код `0`.

**свод.3. Четыре свода, по одному на подшаг.** Каждый: посадить пачку
`--batch=<номера>` (пачка из разных родов идёт без ключа рода); свод делает
сессия по заданию из скилла `bar-probe`, раздел «Задание сессии свода»,
дословно; суд `bar-probe <номер>`; строка цены
`bar-probe --cost --session=<uuid>` — в `.claude/rationale/loop.md`, раздел
«Соразмерность: что читать под задачу» (обязательна по скиллу); коммит и
push. **Промахи и замечания свода об инструменте проверяются, и
подтвердившиеся чинятся до посадки следующей пачки** — с тестами и быстрыми
воротами: иначе дефект инструмента повторится промахом в следующих сводах.

- свод.3.1. В существующем коде.
- свод.3.2. Редкие роды: удаление, сосед, перенос.
- свод.3.3. Новым файлом.
- свод.3.4. Добор в существующем коде.

**свод.4. Разбор того, что осталось от сводов.** Класс — какой формы
нарушения не увидел держатель критерия; места рода — критерии, чей держатель
не видит той же формы, перечнем `bar-hold`; починка в держателе, а не под
посадку; посадка в книгу на каждую форму рода, через ворота стенда.

**свод.5. Перепроверка одной пачкой.** Промахнувшиеся посадки плюс посадки
критериев с тем же держателем. Промах снова — одиночная проба этого
критерия.

Готово, когда: архитектура `30` из `30` и строки `15` из `15` «поймано» с
учётом перепроверки, либо каждый непойманный назван с причиной. Граница
доли промахов — по каждой части отдельно и только на чистом заходе:
архитектура — `10` %, строки — `20` %.

На чём выведено: план `2026-11-02` и разбор того же дня: цена свода почти не
зависит от числа посадок (`6` — `$4.41`, `24` — `$3.4`–`$4.8`), поэтому
сводов четыре, а не пять; правило трёх — `0` промахов на `30` посадках дают
долю промахов не выше `10` % с уверенностью `95` % без поправки на
зависимость внутри свода. Схема «`30` + `15`» решена разработчиком
`2026-11-18`: архитектура — приоритет и держит свою границу `10` %, а
строки, где решает чтение, получают свою — `20` % — без жертвы
архитектурой; прежде посадки шли почти только в архитектуру, и ловчесть
свода на строках не мерилась. Добавить посадки дешевле, чем делить `30`:
цена свода почти не зависит от их числа.

Что будет, если не делать: работники модуля «процесс» опираются на свод,
чья ловчесть на новом коде не мерена.

## Модуль «переход»

Что меряет: условие «посадка» и «смысловая верность» на знакомом проекте с
чужой раскладкой и чужими стилями — **обе стадии**. Переход по
`.claude/seat/transition.md` кончается тем, что обвязка знает проект, а
расхождения записаны долгом с планами; код проекта он не меняет. Приведение
— обычная работа по пунктам долга, по слову разработчика (`code.md` и
`styles.md`, разделы «Проект, устроенный иначе»): пункт приведён — строку
удаляют и обнуляют храповик; обе таблицы пусты — файл перехода удаляют.

Сессия `1` изображает только переход: код проекта она не меняет, итог —
база и долг. Сессии `2`–`4` изображают следующую за ним команду разработчика
«почини»: структура папок вместе с местом тестов, стили, остальной долг.
Итог всех четырёх — проект, неотличимый от посаженного в пустую папку и
написанного с нуля; это мерит шаг `переход.7`. Разбивка на сессии
приблизительная: перенос трогает каждый файл кода, и по правилу «долг
перехода от починки не защищает» (`loop.md`) сессия `2` закрывает тем же
заходом и прочие пункты в этих файлах; сессия `4` сверяет оставшееся с кодом
и берёт то, что не закрыто.

**Остановки — тоже находка.** У каждой сессии модуля наблюдатель смотрит,
где она встала: поле `permission_denials` вывода и вопросы разработчику,
которых задание не требовало. Каждая остановка — находка «встала»: класс —
обход в правилах среды либо причина, снятая в инструменте. Без этого
«без остановок» задачи 2 не мерит никто.

Сессии идут цепочкой: каждая работает на результате предыдущей. Находку,
мешающую следующему звену, чинят до него — тесты по имени, коммит, push;
если починка меняет то, что сделала прошлая сессия, эту сессию повторяют.
Прочие находки ждут шага `переход.8`. После каждой сессии состояние площадки
сохраняется снимком в `workshop/` (справка «Команды и площадки»); снимки
нового захода заменяют снимки прошлого под теми же именами.

**переход.1. Новый составной проект — в корпус.** Написать по справке
«Составной проект — что строить» и записать проектом `composite` в
`.claude/tools/foreign-corpus.json` вместо прошлого (сценарий `familiar`,
поле `axis` — одной фразой, `transitionHas` — пункты, которые план перехода
обязан назвать). Таблицу файлов с колонкой «ожидается» — в данные запуска,
до посадки, по `.claude/seat/transition.md`, раздел «Что идёт в долг
перехода». Ни одно имя проекта не совпадает с именами книги
`bar-probes.json` (справка «Ловушки сборки площадок»). Пакет выше связки —
из шага `посадка.2`, а без «посадки» в запуске — выбранный тем же порядком.
Задания сессий в данных запуска называют компоненты нового проекта. Проверка
шага — корпусный тест по имени `composite`: посадка с кодом `0`, сверка базы
с кодом `0`.

**переход.2. Площадка.** Собрать площадку из проекта `composite` порядком
«площадка из проекта корпуса» справки «Команды и площадки» — тем же, что у
корпусного теста. Сажает её сессия 1.

**переход.3. Сессия 1 — посадка и переход.** Задание: «посади обвязку —
согласие на приведение стека даю, `seat . --apply`; проект — <описание из
данных запуска>; затем сделай переход». Наблюдатель сверяет с колонкой
«ожидается» таблицы составного проекта в данных запуска:

- каждое отклонение стоит пунктом долга с числом, держателем и планом по
  адресам;
- пункты раскладки и стилей называют папку каждого компонента;
- посаженный дефект и слабый тест найдены чтением по планке и стоят
  пунктами;
- шаги знания и шаг `falsify` закрыты;
- протоколы перехода запечатаны;
- `verify` — код `0`.

Не нашлось ожидаемого — находка процесса либо суждения. Снимок
`workshop/composite-transition.bundle`.

С пометкой «с обрывами» стадии приведения идут частями — эмуляция во всех

## Модуль «процесс»

Что меряет: условие «смысловая верность», часть «сессия проходит порядок
работы без пропуска шагов». Рефактор, правку стиля и багфикс проходят сессии
модуля «переход»; здесь — остальные роды задачи.

**процесс.1. Площадка.** Базовая точка — снимок `переход.6` этого запуска,
а без «перехода» — `workshop/composite-baseline.bundle`. Для каждого
работника — свежий клон базовой точки порядком восстановления из
`.claude/README.md`, раздел «Мастерская и проекты»: клон не несёт
`core.hooksPath`, и без неё ворота перед коммитом не стоят. Сессии
независимы: ни одна не видит правок другой. Полка клона — редакции снимка;
если полка правилась после снимка (`git log` по `.claude/` от коммита
снимка), клон сперва получает текущую полку правилом повторного вызова
`seat` (`.claude/tools/graph.md`, режим `seat`): файлы полки копируются
поверх `.claude` клона, снятое на полке снимается, файлы проекта внутри
обвязки — поле `projectOwnedInsideHarness` карты посадки — остаются. Сам
режим клон не обновит: метки посадки у клона нет, — поэтому разовым
скриптом. Обновление коммитится в клоне, `verify` и `npm run check` в нём —
код `0`, и снимок базовой точки сохраняется заново: иначе работники мерят
прежнюю обвязку.

С пометкой «с обрывами» двух работников шага `процесс.3` обрывают и
продолжают по разделу «Пометки к модулям».

**процесс.2. Работник «новый узел» — первым.** Задание вида: «добавь
компонент <новый, связанный с предметом проекта, из данных запуска>; по
завершении закоммить». Заодно замер цены сессии (`bar-probe --cost`); число —
в сообщение коммита. Провалился машинный шаг — ворота, хук конца хода,
печать — остальные пять не запускаются до его починки.

**процесс.3. Остальные пять работников подряд, один шаг на всех.** Задания
пишутся по именам базовой точки — их называет её карта
(`.context/00-map.md`) — и лежат в данных запуска:

- удаление узла — «удали <компонент>, он больше не нужен; закоммить»;
- правка значения-настройки — «подними <настройку> с <было> до <стало>;
  закоммить»;
- правка теста — «тест <компонента> проверяет только отрисовку — добавь
  проверку <действия>; закоммить»;
- ревью без правки — «сделай ревью <компонента>, ничего не меняя»;
- правка одной документации — «допиши в документацию <компонента>, зачем
  у него <два варианта>; закоммить».

Наблюдатель читает пять сводок за один проход, после последней сессии.

**процесс.4. Горячий раунд — проход по держателям-машинам и работник на
хуки.** Один раз на запуск: второй заход «процесса» его не повторяет, если
между заходами не правили ворота, хуки и страж — исход прохода по
держателям однозначен. Порядок — скилл `probe`, правило «Точку, которую держит машина,
пробой руками не берут — её держателя проходят списком»: перечень держателей
командой, у каждого — фальсификация (рецепт `falsify` либо тест
инструмента), держатель без неё получает тест. В перечень входят и точки,
которые прошлые заходы брали пробами:

1. `blast` — радиус у узла с потребителями в разных слоях.
2. `cycles` и `dead` — посаженный цикл и экспорт без потребителя названы.
3. `repoint` — строки, вставленные над якорем, переставлены; `tiers`
   печатает цену ярусов.
4. База в прямую сторону: файл без записи в карте — сверка его называет.
5. База в обратную сторону: запись о файле, которого нет, — сверка её
   называет.
6. Страж: коммит кода с `--no-verify` и с `-c core.hooksPath=` остановлен.
7. Ворота конца хода: ход с неопечатанной правкой кода удержан;
   `stop --pause` с причиной печатается началом следующей сессии; правило,
   изменённое посреди сессии, страж называет.

Руками ставится только проба `7` — сессией-работником в посаженной
площадке: хуки исполняются только в живой сессии, а в мастерской их нет.
Правило меняют на диске посреди хода работника, а не по таймеру: короткая
сессия кончается раньше, и часть пробы проходит мимо. Если ход работника
этого не позволяет — ворота и паузу пробуют живой сессией, а смену правила
прямым вызовом `node .claude/tools/hook.mjs guard --hook`, и в коммите
сказано, какая часть чем проверена (так сделано `2026-11-04`).

Коммит — с пометкой `Probe-run: hot; …`.

**процесс.5. Разбор по классам → починки → повтор только тех сценариев, где
был пропуск → коммит и push.** Шаг, выполненный работником одним вниманием,
получает машинного держателя либо остаётся с записанной причиной, почему
машина его не видит.

Готово, когда: у каждого шага каждого рода исход «выполнено» и держатель
назван.

На чём выведено: план `2026-11-02`; свежая сессия не знает, что её
проверяют, и потому меряет процесс честнее, чем сессия, которая его
изображает.

Что будет, если не делать: шаг порядка работы, который держится одним
вниманием, пропускается первым же живым проектом, и признака у пропуска нет.

**замыкание.5. CI зелёный на итоговом дереве.** Windows вручную

## Справка: составной проект — что строить

Площадка модуля «переход» и база работников модуля «процесс»: знакомый проект, который
переход обязан прочитать, записать долгом с планами, а сессии 2–4 — привести
до «как с нуля». Пишется заново каждый заход: другое приложение, другие
имена, дефект другого критерия. Образцы прошлых прогонов — `a0cd12a`
(карточка магазина, `2026-11-02`) и `7f577ad` (привычки за неделю,
`2026-11-06`): смотреть масштаб, не копировать.

**Размер.** Проект несёт ровно предметы проверок, по одному экземпляру на
форму; код, который не читает ни одна проверка, не пишется. `12`–`17`
файлов, до `300` строк. Небольшое приложение на React с одним предметом,
которое описывается одной строкой задания. Код пишется чистым по типам и
линту: долг типов и линта держит корпус, и здесь он не нужен.

**Что проект обязан нести** — каждая строка одним экземпляром:

| Форма | Чем несётся | Ожидается после перехода |
| --- | --- | --- |
| стек ниже связки | манифест: React `18`, Vite `5`, Vitest `2`, TypeScript `5.6` | план стека поднимает по согласию |
| пакет выше связки | манифест: пакет из шага посадка.2 | план стека опускает к связке |
| версии диапазоном | манифест: `^` у всех пакетов | пакеты осей закреплены посадкой; пакет вне осей — пункт «Версии зависимостей диапазоном» |
| без части звеньев | нет Prettier и Stryker | звенья ставит план стека |
| точка входа в корне src | `index.html`, main.tsx | пункт «Раскладка проекта своя» |
| корень композиции не в src/app | App.tsx с глобальным листом, где лежат классы одного из компонентов | раскладка; схема стилей |
| компонент с вариантом пропом и стилями глобальными классами | файл компонента в корне src; два варианта пропом (размер, тон) | раскладка; схема стилей (папка компонента) |
| тест рядом с файлом, проверяющий только отрисовку | тест того же компонента; нажатие не проверено | «Тесты вне папки `tests/`»; работник правки теста дописывает проверку действия |
| карта классов пропом | компонент получает карту из App; тип карты — запись по любой строке | схема стилей; «Ключи переданной карты классов названы типом компонента» |
| объявление над функцией узла | константа уровня модуля в файле компонента | «В файле узла только сам узел» |
| объект стилей в разметке | третий компонент со стилем объектом | схема стилей (папка компонента) |
| хук без тестов, читающий настройку | хук предмета приложения с пределом из файла настроек | файлы без тестов; «Код под мутациями не мерян» |
| значение-настройка | файл настроек с числом, которое работник правки настройки меняет | файлы без тестов либо документ настроек |
| сборная папка | utils, common, lib — общий код без области | раскладка; возможен факт `levels` «общий узел одной единицы» |
| тест в `__tests__` | тест функции сборной папки | «Тесты вне папки `tests/`» |
| дефект, находимый чтением по планке | функция сборной папки нарушает один критерий планки; каждый прогон — другой критерий (`2026-11-02` — `E2`, `2026-11-06` — `C4`) | пункт долга с критерием и файлом |
| слабый тест | тест той же функции, который дефекта не ловит (`J1`) | пункт долга либо пункт мутаций |
| конфиги своими именами | конфиги сборщика, компилятора, линта проекта | слиты с конфигами обвязки, а не переписаны |

**Что требуют задания модулей «переход» и «процесс»** — проект обязан это иметь: компонент с
двумя вариантами и тестом «только отрисовка» (правка теста, документация);
значение-настройку, которую поднимают (правка настройки); компонент, без
которого приложение работает (удаление); компонент средней сложности

узел).

**Таблица файлов прогона** — путь, что несёт, что ожидается — пишется в
данные запуска до посадки и уточняется корпусным тестом шага переход.1.

## Справка: числа и что они позволяют утверждать

Предметы проверки трёх родов, и считаются они по-разному.

**Детерминированное** — посадка командой, сверки, `falsify`, самопроверки:
тот же вход даёт тот же исход, повтор ничего не добавляет. Мерило — каждый
класс входа один раз: ветка посадки, достижимая входом человека, держится
тестом либо проектом корпуса (шаг посадка.4).

**Стохастическое** — сессии модели. Правило трёх: ноль провалов в `n`
независимых попытках — доля провалов не выше `3/n` с уверенностью `95` %:
`15` попыток — `20` %, `30` — `10` %, `49` — `6` %, `60` — `5` %. Попытки
внутри одной сессии зависимы, поэтому их раскладывают по нескольким
сессиям.

**Поисковое** — холодная ось `probe`: найти неизвестное. Проход по виду
перечисляет его целиком и закрывает тестом — это детерминированное. Выборка
ищет виды, о которых не подумали: чистая выборка из `21` пробы — доля
неизвестного не выше `14` % на пробу. Повтор прогона — по слову
разработчика.

| Что | Сколько | Почему |
| --- | --- | --- |
| холодная ось | проходы, хотя бы один на семейство, и `21` проба, по `3` на семейство, с добором | проход закрывает вид целиком; `21` чистая — не выше `14` %; скилл `probe` |
| корпус | по проекту на ветку кода посадки | шаг посадка.4 |
| `bar-probe` | `30` архитектурных и `15` строковых новых посадок, `4` свода | `10` % без поправки на зависимость внутри свода; цена свода почти не зависит от числа посадок |
| посадки сессией | `2` | знакомый проект сажает сессия модуля «переход» |
| переход и приведение | `4` сессии цепочкой | одна сессия на стадию; пункты долга сверяет машина |
| работники процесса | `6` | роды задачи, не пройденные в модуле «переход» |
| горячий раунд | проход по держателям-машинам и `1` работник на хуки | точку, которую держит машина, держит её фальсификация, а не проба |
| полный набор | раз на модуль с правкой инструмента, и в замыкании — если правили после | раз на пачку правок |
| `falsify`, мутации инструмента, `handoff`, `bar-hold` | по `1` разу на запуск | раздел «Дорогие действия» |

Цена, замеры первых прогонов: свод пробы планки — `$3.4`–`$4.8` за пачку;
сессии перехода и приведения — `9.79`, `14.38`, `17.98`, `3.13` доллара;
работники — от `1.09` (документация) до `6.20` (новый узел) доллара.

**Что будет можно утверждать по итогу:**

Числа — в сообщениях коммитов и в итоге разработчику; в витрину — README
и заметки к выпуску — идут те же утверждения без точных чисел и дат (шаги
выпуск.1 и выпуск.2), не округлённые вверх.

1. Посадка: каждая ветка посадки, достижимая входом человека, держится
   тестом либо проектом корпуса, и каждый проект корпуса садится кодом `0` —
   детерминированно.
2. Переход и приведение: знакомый проект с чужой раскладкой и тремя чужими
   формами стилей проходит переход и доходит до «как с нуля» по машинному
   критерию шага переход.7.
3. Суждение свода: `0` промахов на `30` новых архитектурных посадках — доля
   промахов на архитектуре не выше `10` % (`95` %); `0` на `15` строковых —
   не выше `20` %; без поправки на зависимость внутри свода.
4. Процесс: каждый шаг каждого рода задачи либо держит машина, либо он
   наблюдался без пропуска, с границей `3/n`.
5. Холодный контур: каждый перечисленный вид пройден целиком и держится
   тестом; выборка из `21` пробы нашла столько-то новых видов, а чистая —
   доля неизвестного не выше `14` % на пробу.

## Справка: ловушки сборки площадок

Каждая уже стоила упавшего прогона либо потерянного времени.

**Перед полным набором — дешёвые проверки, которые его роняли.** Полный
набор идёт около `35` минут, CI на Windows — около `65`, и красный в любом из
них стоит повтора обоих. Поэтому до полного набора, по тому, что тронуто:

1. обновить испытательную посадку командой из справки «Команды и площадки»;
2. тесты правленых тестовых файлов — по имени; имя теста, извлечённое
   скриптом, проверить на пустоту: пустой `-t` запускает файл целиком;
3. тронуты книга посадок, данные стенда, корпус либо любой текст в
   `.claude/tools/` — комментарий, справочник, — тест «составное имя посадки
   и прикрытия стоит только своим объявлением файла» по имени;
4. тронута проза полки — правила, скиллы, справочники, todo — `verify` в
   испытательной посадке: там бюджет доктрины, заголовки критериев, числа в
   прозе, команды с переменной оболочки;
5. тронуты книга, стенд либо механизм посадки — ворота стенда
   `bar-probe --stand-check`.
