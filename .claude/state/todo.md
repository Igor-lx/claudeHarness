# Отложенная работа по самой обвязке

Работа с **принятым решением**: что делать, известно, осталось сделать. Где
решения нет — `questions.md` рядом. Отложенное разработчиком как отдельный
вопрос — `parked.md` рядом: его не читают, пока разработчик не вернётся к
пункту.

Едет вместе с обвязкой: перестройка касается доктрины, а не проекта, в котором
она сейчас лежит. Отсюда и требование к записи: **пункт формулируется так, чтобы
он был осмыслен в любом проекте.** Работа по одному конкретному репозиторию —
не отложенное обвязки, и здесь ей не место: у получателя она читается как чужое
дело.

**Закрытый пункт отсюда удаляется целиком**, а не помечается закрытым: в списке,
где половина записей закрыта, перестают читать и открытые.

**Форма записи** — заголовок `## <что сделать>`, следом что именно, на чём
выведено и что будет, если не делать.

**Разделы стоят по полезности** — порядок задан разработчиком `2026-10-16`.
Без другого слова берут верхний; новый пункт ставят на его место в порядке.

**Прогон пробы планки — один на группу, а не на пункт.** Решено
разработчиком `2026-10-16`: прогон стоит около `4.5` доллара и `20` минут,
поэтому его делают один раз, после всех пунктов, которые меняют то, что он
меряет, — суждение свода: политику планки, словари признаков, модель свода,
форму ответа. Остальное держат тесты обвязки, `falsify` и `bar-hold`.

Прогоны групп `2026-10-16` и `2026-10-18` сделаны; записи о них и цена свода —
`.claude/rationale/loop.md`, раздел «Соразмерность: что читать под задачу».

## Как вести работу по пунктам 1–6

Пункты 1–6 — один план, принятый разработчиком `2026-11-02`: довести обвязку
до рабочего состояния на нашем стеке и на этом закончить работу над ней. План
написан для сессии, у которой нет истории той, что его составила: всё нужное
лежит здесь, в `CLAUDE.md` мастерской и в файлах по названным адресам.

**Перед первым шагом — сброс к `origin/main`.** Каждый шаг пушится сразу, поэтому всё неотправленное в контейнере — незаконченный шаг либо остаток прежней работы, и оно сбрасывается, а не разбирается (решено разработчиком `2026-11-02`): `git fetch origin --prune`, `git checkout -B main origin/main`, `git reset --hard origin/main`, `git clean -fdx`, прочие локальные ветки удалить. Незаконченный шаг начинается заново.

**Затем прочитать `CLAUDE.md` в корне мастерской.** Там четыре
правила работы над обвязкой, и план их исполняет: ветка одна — `main`; работа
планируется до начала, и дорогое действие стоит в плане один раз на группу;
цель — рабочее состояние по условиям из него; область гарантий — наш стек, чужое
отсекается классом.

### Шаг — единица работы

Пункт разбит на шаги с номерами вида `2.3`. Порядок исполнения:

1. Взять первый оставшийся шаг первого оставшегося пункта. Шаги и пункты идут
   по порядку: каждый следующий опирается на сделанное предыдущими.
2. Сделать шаг целиком: работа, находки шага, их починка классом, тесты
   затронутого по имени.
3. Удалить сделанный шаг из этого файла той же правкой. Результат шага —
   числа, находки, что починено и как — пишется в сообщение коммита, а не
   сюда: здесь лежит только то, что осталось сделать.
4. Коммит и `git push origin main` — после **каждого** шага, без отдельного
   спроса: это прямая команда разработчика на весь план (`2026-11-02`). Новых
   веток не заводить, даже если среда сессии назначила свою (`CLAUDE.md`).
5. Шаг не помещается в остаток сессии — разбить его здесь же на части,
   сделанную часть удалить, оставшуюся записать шагом, коммит и push.
   Следующая сессия начинает с первого оставшегося шага, ничего не
   восстанавливая по памяти.
6. Пункт пуст — удалить его заголовок. Пусты все шесть — удалить этот раздел
   и все справки плана ниже: файл возвращается к шапке.

Сообщения коммитов — английские, Conventional Commits, как в истории
мастерской.

### Проверки и публикация

- **По ходу шага и перед его коммитом** — тесты затронутого по имени:
  `npx vitest run --config .claude/tools/vitest.config.mjs -t "<имя>"` в
  испытательной посадке (справка «Команды и площадки»), и сверка базы там же.
- **Полный набор — один раз на пачку, последним её шагом.** Пачки плана:
  пункты `2` и `3` вместе; пункт `4`; пункт `5`; пункт `6` — если в нём
  что-то правилось.
  Это правило о дорогих действиях из `CLAUDE.md`.
- **Отступление от `safety.md` принято разработчиком `2026-11-02`.** Там
  публикация наружу — только после полного набора с кодом ноль. Здесь
  промежуточный push идёт после тестов по имени, чтобы работа не терялась
  между сессиями и аккаунтами. Страховка — CI: push, тронувший
  `.claude/tools/**` или `.claude/seat/**`, запускает `harness-windows`
  (полный набор на Windows, около `60` минут) и `harness-bootstrap`.
- **Красный CI или красный полный набор — следующий шаг, впереди всех
  остальных.** Статус CI смотрят инструментом GitHub (`actions_list`, ветка
  `main`).
- **Сообщение коммита последнего шага пачки называет, сколько раз
  запускалось каждое дорогое действие и почему не меньше** — графа отчёта из
  `CLAUDE.md`.

### Находки

Чинятся классом, порядком скилла `probe`, раздел «Найденное лечится как класс,
а не как пример»: класс одной фразой; места рода — командой поиска;
сведение в один механизм; тест на механизм; фальсификация четырьмя
действиями. Находка, которая воспроизводится только в чужом окружении,
чинится только как отсечение: не упасть, не встать посреди работы, назвать в
отчёте (`CLAUDE.md`, «Область гарантий»). Шаг, который сессия-работник
выполнила одним вниманием, — кандидат в машинный держатель: ворота, хук,
сверку.

### Сессии-работники и наблюдатель

Кто такие работник и наблюдатель, как зовут работника, сводка журнала и
перечень шагов с признаками — скилл `probe`, раздел «Работник и наблюдатель».
Наблюдатель здесь — сессия, ведущая план. Образец вызова для площадок плана —
справка «Команды и площадки».

### Экономия — необходимо и достаточно

Во всём плане, решено разработчиком `2026-11-02`: площадка несёт ровно предметы своих проверок, по одному экземпляру на форму, и код, который не читает ни одна проверка, не пишется; наблюдатель читает сводку журнала, а не журнал; проба читает только то, о чём её вопрос; дорогое действие — раз на группу (`CLAUDE.md`). Строгость при этом не снижается: число проб и посадок выведено из того, что нужно утверждать (справка «Числа и что они позволяют утверждать»), а не из бюджета.

## 4. Знакомый проект: переход и приведение до «как с нуля»

Что именно: условие «посадка» и «смысловая верность» на знакомом проекте с
чужой раскладкой и чужими стилями — **обе стадии**. Переход по
`.claude/seat/transition.md` кончается тем, что обвязка знает проект, а
расхождения записаны долгом с планами; код проекта он не меняет. Приведение
— обычная работа по пунктам долга, по слову разработчика (`code.md` и
`styles.md`, разделы «Проект, устроенный иначе»): пункт приведён — строку
удаляют и обнуляют храповик; обе таблицы пусты — файл перехода удаляют.
Проверяется, что переход записал долг верно, а работа по нему довела проект
до состояния «как с нуля».

Сессия `1` изображает только переход: код проекта она не меняет, итог — база и долг. Сессии `2`–`4` изображают следующую за ним команду разработчика «почини»: структура папок вместе с местом тестов, стили, остальной долг. Итог всех четырёх — проект, неотличимый от посаженного в пустую папку и написанного с нуля; это мерит шаг 4.6.

Сессии идут цепочкой: каждая работает на результате предыдущей. Находку,
мешающую следующему звену, чинят до него — тесты по имени, коммит, push; если
починка меняет то, что сделала прошлая сессия, эту сессию повторяют. Прочие
находки ждут шага 4.7. После каждой сессии состояние площадки сохраняется
`git bundle` в папку `workshop/` в корне мастерской: она лежит вне `.claude/`
и с обвязкой не едет. Первым, кто её заводит, дописывается строка о ней в
`.claude/README.md`, раздел «Мастерская и проекты», в перечень файлов самого
репозитория.

Скрипт печатает по каждому из модулей посадки уникальные строки каждого проекта и число строк, которых не прошёл никто. Проверен `2026-11-02` на проектах `empty` и `crlf`: тесты — код `0`; у `empty` своё есть только в `graph.seat.mjs`.

```js
// Unique coverage of the seating code per corpus project.
// Usage: node cov.mjs <coverage root: one folder per project> <shelf tools dir>
import fs from "node:fs";
import path from "node:path";

const [root, tools] = process.argv.slice(2);
const FILES = (process.env.COV_FILES ?? "graph.seat.mjs,graph.seatlive.mjs,graph.profile.mjs").split(",");
const projects = fs.readdirSync(root).filter((p) => fs.statSync(path.join(root, p)).isDirectory());

// project -> file -> list of dumps; a dump is every range of every function of one process
const data = {};
for (const p of projects) {
  data[p] = {};
  for (const f of fs.readdirSync(path.join(root, p))) {
    if (!f.endsWith(".json")) continue;
    let j;
    try {
      j = JSON.parse(fs.readFileSync(path.join(root, p, f), "utf8"));
    } catch {
      continue;
    }
    for (const s of j.result ?? []) {
      const base = s.url.split("/").pop();
      if (!FILES.includes(base)) continue;
      (data[p][base] ??= []).push(s.functions.flatMap((fn) => fn.ranges));
    }
  }
}

// Executed at offset x: in some dump the smallest range holding x has count > 0.
const executed = (dumps, x) =>
  dumps.some((ranges) => {
    let best = null;
    for (const r of ranges)
      if (r.startOffset <= x && x < r.endOffset && (best === null || r.endOffset - r.startOffset < best.endOffset - best.startOffset))
        best = r;
    return best !== null && best.count > 0;
  });

for (const file of FILES) {
  const src = fs.readFileSync(path.join(tools, file), "utf8");
  const lineOf = (x) => src.slice(0, x).split("\n").length;
  const cuts = new Set([0, src.length]);
  for (const p of projects) for (const d of data[p][file] ?? []) for (const r of d) cuts.add(r.startOffset).add(r.endOffset);
  const xs = [...cuts].sort((a, b) => a - b).slice(0, -1);
  const hit = Object.fromEntries(projects.map((p) => [p, xs.map((x) => executed(data[p][file] ?? [], x))]));
  console.log(`== ${file}: segments ${xs.length}`);
  for (const p of projects) {
    const lines = new Set();
    xs.forEach((x, i) => {
      if (hit[p][i] && projects.every((q) => q === p || !hit[q][i])) lines.add(lineOf(x));
    });
    console.log(`  ${p}: unique segments at lines ${lines.size === 0 ? "none" : [...lines].slice(0, 12).join(", ") + (lines.size > 12 ? ` (+${lines.size - 12})` : "")}`);
  }
  const none = new Set();
  xs.forEach((x, i) => {
    if (projects.every((p) => !hit[p][i])) none.add(lineOf(x));
  });
  console.log(`  run by no project: ${none.size} lines`);
}
```

## Справка: числа и что они позволяют утверждать

Предметы проверки трёх родов, и считаются они по-разному.

**Детерминированное** — посадка командой, сверки, `falsify`, самопроверки:
тот же вход даёт тот же исход, повтор ничего не добавляет. Мерило — покрытие:
каждый класс входа один раз. Необходимо — у проекта есть ветка кода, которой
нет у других; достаточно — новая форма не добавляет ветки. Это мерит шаг 2.4.

**Стохастическое** — сессии модели. Правило трёх: ноль провалов в `n`
независимых попытках — доля провалов не выше `3/n` с уверенностью `95` %:
`15` попыток — `20` %, `30` — `10` %, `49` — `6` %, `60` — `5` %. Попытки
внутри одной сессии зависимы, поэтому их раскладывают по нескольким
сессиям.

**Поисковое** — пробы `probe`: найти неизвестное. Чистый прогон из `49`
разных проб — доля необнаруженного не выше `6` % на пробу. Число прогонов
заранее не задаётся: до первого чистого.

| Что | Сколько | Почему |
| --- | --- | --- |
| холодная ось | `49` проб на прогон, до чистого | семь семейств обязательны; `49` дают `6` % |
| корпус | по проекту на ветку кода посадки | замер шага 2.4 |
| `bar-probe` | `37` посадок, `4` свода | `8` % без поправки на зависимость; итог — вместе с журналом прошлых прогонов |
| посадки сессией | `2` | знакомый проект сажает сессия пункта 4 |
| переход и приведение | `4` сессии цепочкой | одна сессия на стадию; пункты долга сверяет машина |
| работники процесса | `6` | роды задачи, не пройденные в пункте 4 |
| горячий раунд | `7` проб | точки, которых не касаются работники |
| полный набор | `4` раза, пятый — если правил пункт 6 | раз на пачку |
| `falsify`, мутации инструмента, `handoff`, `bar-hold`, замер покрытия | по `1` разу | |

Цена: замерен только свод пробы планки — около `4.5` доллара за пачку; цену
сессии-работника меряет шаг 5.2.

**Что будет можно утверждать по итогу:**

1. Посадка: каждая форма, которую различает код посадки, садится кодом `0` —
   детерминированно.
2. Переход и приведение: знакомый проект с чужой раскладкой и тремя чужими
   формами стилей проходит переход и доходит до «как с нуля» по машинному
   критерию шага 4.6.
3. Суждение свода: `0` промахов на `37` посадках — доля промахов не выше
   `8` % (`95` %) без поправки на зависимость; вместе с журналом прошлых прогонов.
4. Процесс: каждый шаг каждого рода задачи либо держит машина, либо он
   наблюдался без пропуска, с границей `3/n`.
5. Холодный контур: чистый прогон из `49` проб — не выше `6` %
   необнаруженного на пробу.
