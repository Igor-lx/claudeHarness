# context — правила и инструменты для нового проекта

> **Этот файл — рабочий, для ассистента:** состав полки, порядок посадки,
> оговорки каждого шага. Человеку нужен другой —
> [`docs/README.md`](./docs/README.md): что это такое, что меняется в работе и
> из чего состоит, без шагов и без оговорок. Разделены они потому, что отвечают
> на разные вопросы, и слитый текст плохо отвечал бы на оба.

Полка содержит не код, а **порядок работы**. Всё, что здесь лежит, выведено на
работающем проекте задним числом: база знаний и правила качества составлялись по
готовому коду. Это дало два убытка, названные в `base.md`: часть причин
восстанавливалась неверно без признака, а объём чтения равнялся всему коду
проекта. Полка существует, чтобы следующий проект начинался с готового набора.

Отсюда её единственное правило: **сажается в проект до первой строчки кода, а не
после.**

## Сначала донор, потом принимающая сторона

У полки две фазы жизни, и обе — у одной и той же папки.

**Фаза первая: донор.** Из неё копируют при настройке обвязки проекта. Посадка
**в полку не записывает ничего** — ни файлов, ни `CONFIG`, ни шаблонов; полка
только читается. Поэтому одна полка используется для любого числа проектов
подряд, и каждый получает одинаковое содержимое.

**Фаза вторая: принимающая сторона.** Как только обвязка встала, та же папка
становится полкой этого места, и дальше **правки идут в неё**: появилось правило,
находка, новая сверка — они дописываются и в проект, и сюда, одной правкой. За
тем, чтобы она не отставала, следят побайтовые сверки и режим `twins`.

Отсюда всё остальное:

- **Новый проект рядом.** Полка уже лежит в этом репозитории; заводится второй
  компонент — она донор для его обвязки и остаётся общей полкой репозитория.
  Никакой второй полки не заводят.
- **Новое место.** Содержимое полки копируют в папку на новой машине — имя любое,
  никакого `shared` там может не быть. С первой же минуты у неё обе роли: донор
  для настройки проекта и полка этого места. Дальше она развивается тут и со
  временем расходится с исходной. Это допустимо: экземпляры самостоятельны.
  Свести их можно только вручную — машинной сверки между разными местами нет.

Практически это значит, что при заведении обвязки достаточно сказать: **где мы,
где проект и где полка.** Остальное — по шагам ниже.

**Полка не обязана лежать внутри проекта.** Своя папка рядом, каталог уровнем
выше, отдельный репозиторий — годится любое место и любое имя; никакого
`src/shared` там может не быть вовсе. В `CONFIG.shelf` пишут путь к ней, хоть
`"../../obvyazka"`. Проверено посадкой: проект и полка соседними папками,
`verify` — код возврата 0.

**Раз полка снаружи — переносить надо всё, чем работают.** Не только тексты
правил: инструмент и его справочник, шаблоны скиллов, шаблон разрешений, шаблон
мутационного конфига. Всё это лежит в полке и всё перечислено в шаге 1; список
там и есть проверка полноты — если чего-то в нём нет, оно останется в старом
месте и обнаружится не сразу.

`CONFIG.shelf` — путь к полке этого места; она есть почти всегда. `null` ставят в
одном случае: проект сознательно обвязку дальше не раздаёт. Тогда побайтовые
сверки выключаются одним движением, а доктрину всё равно копируют — без неё
проект остаётся без планки.

## Как посадить в новый проект

### Как это позвать

Достаточно одной фразы, и она человеческая:

> **посади обвязку, полка в папке `<такой-то>`, проект `<такой-то>`**

Годится любая её форма — «установи полку», «разверни правила в проекте»,
«поставь обвязку отсюда туда». Называть надо ровно две вещи: **где полка** и
**куда сажаем**. Всё остальное — ниже, и пересказывать это в просьбе не нужно:
шаги, порядок и оговорки читаются здесь.

**Чего делать не надо:** объяснять процедуру словами и диктовать шаги. Полка
самодостаточна — в ней всё, что нужно, включая этот файл. Названа папка —
дальше работа идёт по нему.

Не названо что-то из двух — это единственное, о чём спросят до начала. Папки
проекта ещё нет — так и скажите: пустая папка законный случай, посадка на него
и рассчитана.

### Порядок

Порядок проверен пересадкой в пустой проект: пройденный до конца, он даёт
`verify` с кодом возврата 0. Выполняется за один заход; из инструментов нужен
только `node`.

**Что получится в корне проекта:**

```
<корень>/
  CLAUDE.md                  ← из CLAUDE.template.md, заполнить <...>
  .gitattributes             ← из environment.md, до первого коммита
  eslint.config.js           ← из eslint.config.template.js, шаг 4-бис
  .prettierrc.json           ← из prettierrc.template.json, там же
  .prettierignore            ← из prettierignore.template, там же
  .nvmrc                     ← версия среды, шаг 4-бис
  package.json               ← там же появляется команда `check` и `engines`
  .claude/
    settings.json            ← из settings.template.json
    skills/
      task/SKILL.md          ← из task.skill.template.md
      probe/SKILL.md         ← из probe.skill.template.md
      audit/SKILL.md         ← из audit.skill.template.md
      purpose/SKILL.md       ← из purpose.skill.template.md, когда своду будет
                                что выводить смысловым проходом
      README.md              ← из skills.readme.template.md
  .context/                  ← папка базы; имя фиксировано решением
    graph.mjs                ← рабочая копия tools/graph.mjs
    graph.md                 ← его справочник, из tools/graph.md
    graph.predicates.mjs     ← словарь области; инструмент его импортирует
    graph.predicates.test.mjs ← набор на словарь, гоняется прогоном тестов
    rules/                   ← доктрина целиком, копиями из полки: glossary,
                                loop, code, close, quality, quality-scoped,
                                base, base-format, writing, documentation,
                                environment
    00-map.md
    01-facts.md
    02-todo.md
    13-questions.md          ← список вопросов без ответа, можно пустым
  <полка>/                   ← та самая папка: сперва донор, дальше принимающая
                                сторона. Имя любое, лежать может где угодно
```

**Имя папки базы — `.context/`, и это не пример, а часть раскладки.** Свобода
выбора здесь была и снята решением: пока имя могло быть любым, доктрина полки не
имела права назвать ни один файл базы — и говорила обиняками, «инструмент базы
знаний» вместо `graph.mjs`, «реестр решений» вместо `09-decisions.md`. Правило,
потерявшее адрес своего крючка, читается как совет и исполняется как совет.
Отступление от умолчания законно, но оно — **решение**, и правит доктрину в том
же заходе, а не оставляет её врать.

## Как написан текст полки: конкретика или подстановка

Правило одно, и оно избавляет от того, чтобы решать пофразно — а решалось
именно так, и потому непоследовательно: менеджер пакетов назывался прямо в
нескольких местах и обиняком в соседних.

> **Конкретика — там, где предмет задаёт сама полка. Подстановка — только там,
> где проект действительно волен выбрать.**

Полка раздаёт инструмент, его режимы, имена файлов базы, раскладку скиллов и
папку `.context/` — значит называет их **своими именами**. Список того, что
остаётся за проектом, закрытый:

| Переменное | Где задаётся |
| --- | --- |
| корень исходников | `CONFIG.src` |
| путь к полке либо её отсутствие | `CONFIG.shelf` |
| команды проверок, если менеджер не `npm` | таблица проверок в `CLAUDE.md` проекта |
| наличие форков, решений, таблиц настроек, выключений линта | поля `CONFIG`, и прогон сам краснеет, когда предмет появился |

Всё, чего в этой таблице нет, пишется конкретным адресом. Новая переменная
заводится только вместе со строкой в этой таблице.

### Случай едет, адрес остаётся

Планка требует: **правило записывается вместе со случаем, на котором оно
выведено** (`quality.md`) — без случая правило невозможно проверить, а при
сокращении текста оно удаляется первым как утверждение без обоснования. На полке
это требование исполняется в **обезличенной** форме, и граница проходит внутри
самого случая:

| Часть случая | Куда |
| --- | --- |
| что было куплено и за сколько: класс провала, механика, цена | **на полку** |
| адрес: имя продукта, файл, номер строки, деталь этого проекта | **остаётся в проекте** |

Образец — в `code.md`, правило о петле перед новым тестом: «проверка в
браузере писалась как оснастка, петля была пропущена, и в тест уехал способ
ввода, которого движок не принимает». Класс, механика и цена на месте; ни
названия продукта, ни файлов, ни номеров строк — у читателя нового проекта их
всё равно нет, и он прочёл бы их как чужой шум.

**Записано потому, что до сих пор держалось практикой.** Правило про случай
есть, правило про конкретику есть, а что делать со случаем, чей адрес
проектный, не говорил ни один из них — и следующий проход по обобщению снял бы
случай целиком, вместе с опорой правила. Порога это не двигает и ничего не
вытесняет: форма уже действует, здесь она только названа.

Появляются позже и в дерево не входят: `stryker.config.json` — с первыми
тестами (шаг 8), `.context/11-readiness.md` — с первой сверкой готовности.

### Шаг 1. Скопировать из полки в проект

Копируют **по этой таблице**. Полка на этом шаге только читается. Числа здесь нет
намеренно: строк прибавлялось, и счёт за ними не поспевал.

| Откуда (полка) | Куда (проект) | Что потом сделать |
| --- | --- | --- |
| `tools/graph.mjs` | `.context/graph.mjs` | поправить `CONFIG`, шаг 2 |
| `tools/graph.md` | `.context/graph.md` | ничего: справочник режимов, едет как есть |
| `tools/graph.predicates.mjs` | `.context/graph.predicates.mjs` | ничего: словарь едет как есть. **Забыть его нельзя** — инструмент импортирует его первой строкой и без него не стартует |

рабочая, она правится вместе с проектом; полка — место, откуда те же правки
попадают в следующий проект.

**Саму полку в новое место переносят целиком** — она там станет и донором, и
принимающей стороной. Не переносят только тогда, когда проект сознательно не
будет раздавать обвязку дальше; тогда в `CONFIG.shelf` ставят `null`.

### Шаг 2. Поправить `CONFIG` в `.context/graph.mjs`

Блок `CONFIG` в самом верху файла — **единственное место, где задаются пути и
имена.** Обычно трогают эти:

- `src` — путь к исходникам относительно папки базы (по умолчанию `"../src"`);
- **`shelf` — свою полку или `null`.** Кладёте комплект к себе (шаг 1, последний
  абзац) — укажите путь к нему; не кладёте — `null`, и все побайтовые сверки
  полки выключатся разом. Раньше это были семь разных полей, и посадка без полки
  требовала погасить каждое: инструкция называла одно, а падало на шести. Найдено
  пробой;
- `rulesManifest.rules` — **список файлов правил**. У нового проекта он один:
  `"../CLAUDE.md"`. Вложенные `CLAUDE.md` в папках заводят позже, по мере того
  как появляются правила, действующие только там, — и тогда же дописывают сюда.
  Заявленный, но отсутствующий файл роняет прогон намеренно: это значит, что
  файл правил потеряли;
- `adr`, `lintExceptions`, `configDocs`, `lintConfigOff` — `null`, пока в
  проекте нет ни решений, ни исключений линта, ни таблиц настроек со своими
  документами. Ронять посадку они не станут и с чужими адресами: каждая сверка
  сначала смотрит, есть ли предмет. **Вписывать адреса, когда предмет
  появится, напоминание не требуется:** прогон завершается ненулевым кодом со
  строкой «сверки, выключенные при живом предмете». Без этой сверки посадочное
  умолчание сохранялось после появления предмета, не давая никакого признака, и
  проект работал с выключенными проверками неограниченно долго. Найдено пробой на
  вопрос «начнёт ли новый проект с выключенных сверок»;
- `questions` — файл списка вопросов без ответа (`13-questions.md`). Заполняется
  сразу: при `null` вопрос разработчику существует только в тексте отчёта и не
  сохраняется до следующего захода;
- `doctrineCopies` — папка, куда доктрина скопирована в проект (`"rules"`).
  **Обязательно, если доктрину копировали**, а копируют её всегда: без этого
  поля первый же прогон краснеет на адресах внутри неё. Доктрина пишется для
  любого проекта и называет соседей по полке — шаблон разрешений, образцы форм
  записи, — которых в проекте нет и быть не должно;
- `doctrineReading` — шаблон правил и **дословные** заголовки двух его
  разделов: списка файлов доктрины и раздела входа. По ним сверяется, что
  каждый файл доктрины назван в порядке чтения, а не только лежит на полке.
  Заголовок, переписанный своими словами, роняет прогон — это сделано
  намеренно, иначе он дал бы пустой разбор, а пустой печатается нулём;
- `rulesHeading` и `isolationHeading` — **заголовки таблиц слоёв, дословно.**
  Инструмент ищет их по тексту заголовка; заголовок, написанный иначе, даёт
  пустой разбор, а пустой разбор печатается как «нарушено: 0». Таблицы в проекте
  нет — ставят `null`, и сверка не выполняется; таблица заявлена и не найдена —
  прогон завершается ненулевым кодом.

**Если полку взяли с собой, после правки `CONFIG` скопируйте рабочий файл в свой
комплект.** Сверка требует побайтового совпадения, а `CONFIG` только что
изменён. **Донор при этом не правят** — правится копия внутри проекта, и она
содержит `CONFIG` этого проекта.

Остальное трогают, только если файлы базы называются иначе, чем в примерах. С
одной оговоркой, стоившей красного прогона на пробе: **в `docPathExceptions`
удаляют только строки, помеченные проектными.** Помеченные полочными описывают
файлы самой полки; если комплект взят с собой, они остаются нужны, а если нет —
удаляются вместе с остальными.

### Шаг 4-бис. Собрать цепочку проверок

Три вещи по порядку: сперва **чем** проверять, потом одна команда, потом версия
среды. Порядок не формальный — команда, вызывающая инструмент, которого нет,
падает сообщением менеджера пакетов, из которого не следует ни что ставить, ни
как настраивать.

#### Инструменты цепочки: поставить и настроить

Полка сажается **до первой строчки кода**, поэтому исходить надо из того, что в
проекте нет ничего. Что нужно цепочке и в каком виде:

| Звено | Чем обычно | Настройка | Что держит настройка |
| --- | --- | --- | --- |
| типы | компилятор TypeScript | руками: `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noUnusedLocals` | эти флаги и объясняют форму кода — `!` после индексации, `?: T \| undefined`. Без них строгость объявлена и не проверяется |
| линт | ESLint + `typescript-eslint` + `eslint-config-prettier` | **шаблоном:** [`eslint.config.template.js`](./eslint.config.template.js) → `eslint.config.js` | линт с типами: без информации о типах правила, которым она нужна, не срабатывают и не сообщают об этом. Плюс правила хуков во всём репозитории и **отключение форматирующих правил линта** |
| формат | Prettier | **шаблонами:** [`prettierrc.template.json`](./prettierrc.template.json) → `.prettierrc.json` и [`prettierignore.template`](./prettierignore.template) → `.prettierignore` | ширину строки, при которой дифф умещается без переноса, и исключение сгенерированных файлов из проверки |
| тесты | раннер под вид проекта | руками | шаблона нет намеренно: конфиг раннера зависит от того, что за проект, и шаблон врал бы чаще, чем помогал |

**Шаблоны едут только у двух звеньев, и это решение, а не недоделка.** Конфиги
линтера и форматтера реализуют **записанные правила** — про хуки, про типы, про
то, что форматтер и линтер не спорят. Конфиг компилятора и раннера реализует
устройство конкретного проекта, и привезённый шаблон был бы догадкой о нём.

**За тем, чтобы шаблон не отстал от проекта, машины нет — и это названо, а не
спрятано.** Побайтовая сверка тут невозможна по устройству: у проекта свои
послабления, и шаблон обязан оставаться обобщённым. Правило поэтому текстовое и
узкое: **в шаблон едет правка того, что он держит** — правило линта, включённое
для всех, отказ от форматирования в линте, ширина строки, — и **не едет**
проектное послабление под конкретную папку. Признак простой: если правку
пришлось объяснять именем своего модуля, она проектная.

**Инструмент ставится вместе со своей настройкой, одной правкой.** Поставленный
без настройки — дефект: чинится в том же заходе, а не заносится в отложенное.
Критерий выполнения: пакет объявлен в манифесте и его конфиг лежит на месте.

Почему требование именно такое. Отсутствующий инструмент виден сразу — команда
падает. Настроенный кое-как завершается нулевым кодом, не проверив ничего, и
цепочке начинают верить. Два места, где это происходит тише всего: линт без
проверки типов (правила, которым нужен тип, просто не срабатывают, а конфиг
выглядит рабочим) и линт без `eslint-config-prettier` (два инструмента спорят об
одних строках, правка под один ломает другой).

**Прогон об этом спрашивает сам, но не запрещает.** Секция «Инструменты обвязки»
печатается, только когда чего-то нет, и называет звено, чего не хватает, зачем
оно и есть ли для него шаблон. Прогон она **не роняет**: набор у проекта может
быть другим — один инструмент вместо пары, другой раннер, — и завершение прогона
ненулевым кодом на этом основании было бы срабатыванием на законном. Свой набор
объявляют в `CONFIG.toolchain`: проверяется только перечисленное там.

Сверка заведена по пробе, и пробел был не гипотетическим: инструкция предписывала
собрать цепочку проверок и **нигде** не называла, откуда берутся её инструменты.
Проверено на рабочем дереве: при отсутствии линтера в манифесте прогон завершался
кодом ноль и не печатал об этом ничего.

#### Одна команда и версия среды

Две строки в манифесте проекта, обе окупаются в первый же день:

- **`check`** — цепочка из всего обязательного набора: типы, линт, формат,
  тесты, сверка базы. Отдельные вызовы держатся памятью и порядком, один — нет,
  и он же останавливается на первом красном. Заведя команду, **допишите её в
  список разрешений** — иначе первый же прогон встанет на подтверждении. Сборку и браузерный смоук в
  цепочку не кладут: первая обычно дублирует проверку типов, второй гоняется по
  требованию.
- **версия среды** — `engines` плюс файл версии (`.nvmrc`), и в `CONFIG.manifest`
  указать, откуда инструмент возьмёт диапазон. Полка обещает переезд на новую
  машину, и **прогон сам скажет, если версия не та**: секция «Версия среды»
  печатается только при расхождении и прогона не роняет.

  Три свойства этой секции — решение, а не умолчание. **Не запрещает:** жёсткий
  вариант (`engine-strict=true` в `.npmrc`) сверяет требования каждой
  зависимости, а не только проекта, и падает на живом дереве из-за
  dev-инструмента — цена измерена, польза меньше. **При подходящей версии
  проверка ничего не печатает:** строка о совпадении версии в каждом прогоне
  увеличивает вывод без повода. **При неподходящей — печатает:**
  разработчик обязан быть предупреждён, а решение дальше — его.

  Заметьте, чего эта секция НЕ обещает: от версии зависят прежде всего **времена
  прогонов**, а они и так зависят от машины. Число тестов и покрытие определяет
  код, размер бандла — версии сборщика из файла блокировки. Поэтому запрет и не
  окупался: он защищал от поломки, которая приходит громко — инструменты падают,
  а не выдают тихо другие числа.

**Пути внутри поправить под проект сразу** — шаблоны называют адреса, которых у
вас пока нет, и `verify` их проверяет. Взяли комплект с собой — скопируйте
поправленный файл и в него: сверка требует побайтового совпадения. Донор, как и
везде, не трогают.

Отсюда правило для текста скилла: **пути — проектные, слова — нейтральные.**
Название своего продукта в описание не вписывать; оно уедет в следующий проект и
будет там врать. Поймано пробой: в описании стояло имя продукта.

**Скилла-установщика здесь нет, и это решение, а не пробел.** Он был заведён и
снят в тот же день: скилл, который умеет только «прочитай `README.md` полки и
пройди его шаги», не добавляет к вызову ничего — постановка задачи и так
умещается в одну фразу, а дублировать шаги внутрь него нельзя, две копии
инструкции разошлись бы при первой правке.

Отсюда **критерий для любого следующего скилла:** он окупается, когда заменяет
длинную постановку, которую иначе пришлось бы повторять дословно — как `probe`
заменяет определения пробы, раунда, прогона и норму фальсификаций. Он не
окупается, когда постановка и так умещается в предложение.

Попутно измерено и записано, чтобы не пробовать второй раз: скилл, положенный
в `<папка>/.claude/skills/<имя>/SKILL.md`, командой `/<имя>` **не становится**,
если эта папка не та, с файлами которой идёт работа. Проверено прямым вызовом —
ответ «Unknown command».

Скиллу `audit` нужен ещё файл памяти в базе — прошлые оценки и **реестр
отклонённого**. Он заводится при первой сверке; до неё его отсутствие ничему не
мешает, а вот без него вторая сверка предложит то, от чего уже отказались.

Заодно объявить состав: строка на каждый скилл в таблице «Скилл / Шаблон на
полке» в `01-facts.md` — её сверяет `verify` трижды. И помнить, что **новый
скилл текущая сессия не увидит**: перечень собирается на старте, нужен
перезапуск. Подробности — в [`environment.md`](./environment.md).

**На этом посадка закончена — дальше можно писать код.** Правила уже действуют:
качество сверяется по `quality.md`, работа идёт по петле из `loop.md`, база
наполняется вместе с кодом.

### Шаг 8. Уже по ходу работы, когда появятся первые тесты

Единственный шаг, который делают **не при посадке**: положить
`stryker.template.json` как `stryker.config.json` в корень и заполнить в нём
`mutate` — область прогона. До первых тестов он бесполезен, поэтому и стоит
после черты, а не в ряду остальных.

## Почему именно так

То, ради чего всё это заведено. Каждое стоило отдельного разбора:

- **Правило без машинной проверки перестаёт исполняться, не давая признака.**
  Договорённость, записанная только в README, нарушается не намеренно, а потому
  что файл не прочитан в нужный момент. Поэтому всё, что можно проверить
  инструментом, проверяется инструментом, а текст объясняет причину.
- **Найденный дефект исправляется, а не описывается.** Раздел, отведённый под
  известные дефекты, наполняется ими, а документация об опасном
  коде делает опасный код разрешённым.
- **База ведётся по ходу правки, а не восстанавливается потом.** В момент написания причина решения
  ещё известна. Через месяц её придётся выводить из кода, и часть выведется
  неверно — причём незаметно.
